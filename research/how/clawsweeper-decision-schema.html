01 · 全局形状

先规定“必须说什么”，再规定“可以怎么说”

schema 的顶层只有五个关键字：$schema、type、additionalProperties、required、properties。没有 $id、没有版本号、没有顶层 description——所有语义都藏在 71 条字段级 description 里。它要解决的不是“怎样写得更漂亮”，而是下游怎样确定自己没有漏读。

“空”不是“没写”。schema 为每种空状态规定了固定形状：字符串用 ""，数组用 []，未知对象用 null，无需人工裁决时用 {required:false, kind:"none", question:"", rationale:"", options:[], likelyOwner:{person:""}}。这样记录可以逐字段 diff，也能区分“没有风险”和“模型忘了填风险”。schema:235-361, 554-624

02 · 裁决核心

先给结论，再给 17 种可解释的关闭理由

四个字段构成最小裁决：decision 只有 close / keep_open；confidence 只有 high / medium / low；summary 承担面向人的一句话结论。closeReason 则把“为什么关”拆成 17 个枚举值，其中 16 个是真实理由，最后一个是显式的 none。

// 最小裁决形状（字段均为必填） { "decision": "close", "closeReason": "implemented_on_main", "confidence": "high", "summary": "The requested behavior already ships on main; closing as implemented." }

枚举的意义是“把拒绝理由也标准化”。none 不是漏填，而是一个合法状态；它通常与 keep_open 配对。但注意：schema 本身没有 if decision=keep_open then closeReason=none 这样的条件约束——配对关系由下游确定性代码保证。这是整份 schema 的典型分工：这里管形状，代码管一致性。schema:69-89

产品 / 范围类理由还多一道人工闸门。按 prompts/review-close-reasons.md，unconfirmed_product_direction、unsponsored_feature_request、clawhub、not_actionable_in_repo 只是建议：评审必须同时设置 maintainerDecision.required=true 与 kind=product_direction，而且 apply 从不执行这些产品拒绝，仍要维护者走普通手动关闭流程。schema 给出理由枚举，prose 与代码决定它能不能落地。prompts/review-close-reasons.md

03 · 唯一显式交还决定权的字段

maintainerDecision：要么明确“无需裁决”，要么给出 2–3 个可选项

这是整份 schema 里最像“产品设计”的部分。它用一个两分支的 anyOf 强制模型区分两件事：没有未决问题，和有未决问题但证据无法替人做决定。不允许用一段模糊的 prose 蒙混过去。

BRANCH A · 无需裁决

空决策也是完整对象

  • required: false（唯一允许的布尔值）
  • kind: "none"
  • question: ""、rationale: ""
  • options: []（上限 0）
  • likelyOwner.person: ""

schema:235-291

BRANCH B · 需要维护者拍板

问题、理由、选项、推荐、负责人

  • required: true
  • kind ∈ product_direction / security_boundary / proof_sufficiency / release_inclusion / merge_risk / manual_review
  • question 与 rationale 必须非空
  • options 2–3 个，每项含 title、body、recommended
  • likelyOwner.person 必须来自 likelyOwners

schema:292-361

“恰好一个推荐项”写在 description 里，不写在 schema 里。选项的 recommended 只是布尔值，schema 没有 minContains/maxContains 去强制“有且仅有一个 true”。同样，likelyOwner 是否真的出现在 likelyOwners 里，也要靠代码交叉检查。读这份 schema 时要始终区分：哪些是机器强制的，哪些是写给模型和 reviewer 的规范。schema:319-360

04 · 解释层与证据链

让新人看懂，同时让 reviewer 能逐行复核

解释层不是“补充说明”，而是决策的一部分。changeSummary 要求用一句中性的话说明 PR 改了什么或 issue 要什么；changeExample 要求给出带真实值的 scenario / before / after；systemContext 说明子系统在系统中的位置与输入输出；architectureDiagram 则限定为 4–8 个节点的纯 Mermaid flowchart，禁止 fences、click、URL、HTML 与 init/style 指令。

evidence：一条证据 = 一个可复核定位符

  • repo：核验过的 owner/repo，未知时为 null
  • label / detail：证据类别与具体结论
  • file / line：精确到行；不适用时为 null
  • command：单行、只读命令；多行时为 null
  • sha：完整 commit SHA，禁止用目标项依赖上的 SHA 冒充

schema:127-162

likelyOwners：1–5 人，角色中性

  • person：GitHub handle 或姓名，禁止邮箱
  • role：feature owner、area contributor、reviewer、merger；只有有证据时才能写 maintainer
  • commits / files：相关提交与文件
  • confidence：high / medium / low
  • history：指向此人在 review checkout 上写过/提交过的一行；无则 null

schema:163-223

这套证据结构的核心是“可证伪”。不是“我看了代码”，而是“在哪个 repo、哪个文件、哪一行、哪个 SHA、用什么只读命令看到的”。history 还把“谁熟悉这块”从模糊印象变成 commitSha + sourcePath + sourceLine + actor 的锚点。schema:203-222

05 · 标签系统

标签不是装饰：每个标签都要有理由，而且数量有上限

ClawSweeper 把“分诊”拆成四个正交维度：优先级、影响面、合并风险、成熟度。它们分别有独立的枚举与上限，最后再由 labelJustifications 逐项解释。这个设计把 GitHub 标签从“维护者手工贴的便利贴”变成了可被 schema 约束的决策输出。

字段适用范围上限允许值 / 语义
triagePriorityissue / PR1P0 紧急（数据丢失、安全绕过、崩溃循环、核心不可用）；P1 紧急回归；P2 普通；P3 低风险清理/文档/打磨；none 不打标
impactLabels仅 issue≤ 39 值：data-loss、security、crash-loop、message-loss、session-state、auth-provider、ux-release-blocker、ux-friction、other
mergeRiskLabels仅 PR≤ 38 值（字符串内含 🚨）：compatibility、message-delivery、session-state、auth-provider、security-boundary、availability、automation、other
maturityLabels仅 issue≤ 1仅 maturity:stable：M4/M5 主 owner 面上的契约行为损坏
mergeRiskOptions有未决风险时≤ 3每项含 title / body / category（fix_before_merge、accept_risk、pause_or_close）/ recommended
reviewMetricsPR 事实—label / value / reason，例如 production vs test LOC 及增长是否合理
labelJustifications每个已选标签—22 个标签值；reason 必填；选 other 时必须点名真实影响/风险

上限是治理手段。影响面最多 3 个、合并风险最多 3 个、成熟度最多 1 个，避免“把所有标签都贴上”这种无效分诊。labelJustifications 的 22 个枚举值正好覆盖 P0–P3 + 9 个 impact + 1 个 maturity + 8 个 merge-risk；但它没有在 schema 层强制“每个已选标签恰好一条 justification”，这仍是下游的一致性检查。

06 · Issue 诊断

把“能不能复现、该不该做、能不能自动修”拆成独立问题

Issue 分支的字段不是一串同质标签，而是一条诊断流水线：先分类，再判断复现，再判断是否引入新能力/新配置/产品决策，最后给出可实施性与根因聚类。这样下游才能分别回答：这是不是 bug？我们能不能看到？值不值得做？能不能交给自动修复？

07 · PR 评审

证明质量、补丁质量、产品判断，三条线分开打分

PR 分支把“这个 PR 好不好”拆成多个不可互相替代的维度：测试证明路径、真实行为证据、引入的 bug、安全问题、产品价值、是否尊重既有意图，最后才合成一个总体等级。这样 reviewer 能看到分数背后的分歧，而不是只看到一个 S/A/B/C。

08 · 关闭证据与回归

“已修复”必须落到 release、SHA、时间和那一条引入行

对 implemented_on_main / mostly_implemented_on_main，schema 要求 fixedSha（修复 commit）；若 fixedRelease 为 null（仅 main），则还要 fixedAt（ISO-8601）。closeComment 则规定了公开评论的骨架：开头一句结论、空行、证据 bullet（原因、Codex review、被 credited 的讨论、路径、release、SHA 或修复时间），证据薄弱时附上 reopen 邀请并点名缺什么。

REGRESSION · 是不是回归

regressionAssessment

  • confidence：suspected（1 类直接证据）/ probable（2 类）
  • supportingEvidence 1–3 项：reproduction、reviewed_change、failure_trace、known_regression_link

时间、历史、标题相似、相关性都不算证据。

schema:971-991

PROVENANCE · 是谁引入的

regressionProvenance

  • repo
  • pullRequestNumber / pullRequestUrl
  • mergeCommitSha：40 位十六进制
  • sourcePath / sourceLine

定位的是“在 review revision 上引入那条责任源码行”的已合并 PR；未知时整体为 null。

schema:992-1027

两层溯源，避免“大概是谁弄坏的”。第一层 regressionAssessment 判断“现在是否构成回归、证据够不够”；第二层 regressionProvenance 精确到“哪个已合并 PR、哪个 merge commit、哪一行”。两层都允许 null，但一旦给出，就必须是可复核的强标识。

09 · 工作路由

“建议怎么做”与“谁有权去做”被彻底分开

最后九个字段负责把结论路由到下一步，但它们刻意不授予任何执行权限。workCandidate 只有三种：none、manual_review、queue_fix_pr；workConfidence 与 workPriority 各为 high / medium / low；workReason 同时承担路由理由与 issue 的 next-action 指引。

字段作用关键约束
nextStepPR 的下一步意图两分支：{kind:"none", text:""} 或 {kind:"required"|"maintainer", text:非空}。只是意图，不是修复/合并授权。legacy required 记录始终视为 contributor work，与 prose 无关
workPrompt可直接交给执行者的任务提示自由文本
workClusterRefs相关工作簇引用字符串数组，用来限定上下文
workValidation完成工作的验证要求字符串数组
workLikelyFiles最可能改动的文件字符串数组，用来估计爆炸半径

能力（capability）不等于权限（authority）。schema 可以让模型写出“该怎么修、改哪些文件、怎么验证”，但 nextStep 的 description 明确写着：never authority to fix or merge。真正的写操作仍要经过下游的 apply 闸门：重取 live GitHub 状态、检查标签/作者/配对 issue/PR/快照漂移。结构化输出越完整，越不能被误读为执行许可。schema:1044-1102

10 · 设计哲学与边界

它强在哪里，以及它故意不管什么

01 · TOTALITY

全量必填

57/57 必填，31 个对象全部封闭。记录之间可以逐字段比较，不存在“这个字段这次没出现”的歧义。

02 · ENUMS FIRST

枚举优先

51 处枚举、237 个允许值。自由文本只用于 detail、summary、reason 这类解释性内容，关键状态不允许即兴发挥。

03 · EVIDENCE

证据可复核

repo + file + line + full SHA + 单行只读 command。证据不是链接集合，而是可定位、可重放的检查点。

04 · CONFIDENCE

置信度分层

high/medium/low、0–1 分数、S–F 等级、suspected/probable。结论与“有多确定”始终一起输出。

05 · AUTHORITY

角色与权限分离

模型可以建议、聚类、写 workPrompt，但 maintainerDecision 把未决选择交还给人，nextStep 不授予写权限。

06 · BOUNDS

边界化输出

owners 1–5、impact/merge-risk ≤3、cluster members ≤12、provenance ≤8、nextSteps ≤3。限制数量就是限制噪音。

要看清 schema 的边界：它管形状，不管一致性。例如 closeReason=none 与 decision=keep_open 的配对、fixedSha 对 implemented_on_main 的依赖、options 中“恰好一个 recommended”、labelJustifications 与已选标签的一一对应，都只写在 description 里，没有 if/then、dependentRequired 或 minContains/maxContains 来强制。它们由确定性代码、apply gate 和测试来保证。

这也是一种演进成本。没有 $id、没有版本字段，且所有对象都 additionalProperties:false：新增一个字段意味着所有生产者都必须同步产出，否则记录不再合法。schema 用“严格”换来了可审计性，代价是变更必须显式协调。读它时，既要看它约束了什么，也要看它把哪些责任留给了代码。
