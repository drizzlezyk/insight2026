1先把“谁在写标签”定义清楚

Issue 不是由单一机器人打标。同一张 issue 上至少叠着四个写入者，各自拥有互不重叠的标签族：

issue template		 bug · enhancement · docs 提交瞬间 纯表单选择：Bug 表单 → bug；Docs Bug → bug + docs；Feature → enhancement。无模型参与。

和 PR 最大的结构差异：D 层不是一次写完的。P、impact、maturity 属于“主评审发布”；issue-rating: 和 12 个咨询标签属于“advisory 同步”，只有在 issue 仍开启、评审完整且当前、且不是关闭提案时才执行。原因是 linked-pr-open 依赖实时 GitHub 状态，不能在发布瞬间冻结。

3写入顺序：一次评审，两个发布时刻

主评审发布（clawsweeper-apply-report-labels.ts:171–205）的顺序是固定的，每一步都是“先删同族旧标签，再写新值”：

syncIntakeLabels(wanted: [])          // 清空预备标签
→ syncPriorityLabel(P0…P3)            // 单选
→ syncImpactLabels(impact:*, ≤3)      // issue 才写；PR 强制 []
→ syncMaturityLabels(maturity:stable) // issue 才写；PR 强制 []
→ [PR 专属] merge-risk → proof → rating → feature → status

issue 的第二次同步（同文件 :227 起）只在四个条件同时成立时运行：state === "open"、kind === "issue"、非关闭提案、报告完整且当前。它写入 issue-rating: 和 12 个咨询标签，并在 queueable-fix 出现时附加 no-stale、移除 stale；标签消失时只回收它自己加的那一个 no-stale。

这套顺序意味着一个可验证的推论：任何一个仍带 clawsweeper:intake:* 的 issue，都还没有完成一次完整评审。实测 100 个近期开放 issue 中只有 1 个仍带 intake 标签。

5.1 impact 与 maturity：issue 专属的两个路由信号

impact: 只在 issue 上写（PR 分支被强制 []），允许最多 3 个，但实测 92% 的 issue 只有 1 个。它不是严重度，而是“问题落在哪条产品面”，用于把 issue 路由给对应的 owner：

impact:ux-friction 6,648 impact:session-state 6,640 impact:other 5,029 impact:message-loss 4,672 impact:auth-provider 3,717 impact:security 3,189 impact:crash-loop 2,058 impact:ux-release-blocker 1,843 impact:data-loss 863

maturity:stable 是单一值标签（3,569 个）：只有当 issue 描述的是“已被 M4/M5 评分卡覆盖的既有行为损坏”时才写。它回答的是“这块行为有没有成熟度基线可对照”，和 P、rating 都正交。

三个质量轴不要混读：P0–P3 说影响面，impact:* 说产品面，issue-rating: 说证据强度。maturity:stable 则标记“有基线可回归”。同一个 issue 可以同时是 P1、impact:auth-provider、issue-rating: 🦞、maturity:stable——四个标签各说各的，不构成一个总分。

6.4 谁在关：全量关闭者分布

对窗口内已关闭 issue 逐条读取最后一次 ClosedEvent：13,028 条记录中 13,024 条可归属到具体关闭者（4 条无法解析）。在可归属记录中，clawsweeper[bot] 关闭 3,252 个（25.0%），openclaw-barnacle[bot] 的 stale 清理关闭 1,632 个（12.5%），机器人合计 4,884 个（37.5%），人类账号 8,140 个（62.5%）。

两类机器人的形态不同：ClawSweeper 的 3,252 个里 1,577 个标 completed、1,675 个标 not planned，且 3,240 个是直接关闭、只有 12 个伴随 PR 合并；Barnacle 的 1,632 个全部是 not planned 的 stale 清理。人类关闭则高度集中且以 PR 合并为主：steipete 一人关闭 4,038 个（占全部关闭的 31.0%），其中 2,872 个是合并 PR 时关闭。

ClawSweeper 对 issue 可用的关闭原因共 9 条：implemented_on_main、cannot_reproduce、clawhub、duplicate_or_superseded、unsponsored_feature_request、stale_version_bug、not_actionable_in_repo、incoherent、stale_insufficient_info。另有 8 条 reason 仅适用于 PR；none 表示保持开启，不算关闭路径。依据 src/clawsweeper-close-reasons.ts 与 src/clawsweeper-policy.ts。

关闭者按最后一次 ClosedEvent 的 actor 归属；机器人指 GitHub Bot 类型账号。另有 roboclaw-bot（GitHub 类型 User，449 个，主要在 PR 合并时关闭）未计入机器人。

7三个结论

Issue 标签是分流系统，不是评分系统

P 和 issue-rating: 描述“问题有多严重 / 证据有多强”，但它们不改变 issue 的去向。真正决定去向的是 5 个 work-lane 标签：queueable-fix（自动修）、linked-pr-open（已有人修）、needs-maintainer-review、needs-product-decision、needs-security-review。读 issue 时先看这五个，再看 P 和评级。

唯一接近“承诺”的标签是 queueable-fix

79% 的 completed 关闭率、5.8 小时中位完成，均显著优于基线（52%）。它同时会自动挂上 no-stale，等于给 issue 一个“不会被清理”的保票。但窗口内只有 12% 的 issue 拿到它——系统的主流结局仍然是“转人工”，而不是“自动修”。

P 与评级都不预测速度，甚至方向相反

P3 的 completed 中位 1.5 h，P0 是 11.5 h；A 档 3.1 h，S 档 11.6 h。越严重、证据要求越高，闭环越慢——因为“完成”需要真实修复，而不是快速分诊。这一点与 PR 侧完全同构：P3 1.12 h 快于 P0 3.27 h。把 P 当作 SLA 会读反。

9局限与引用口径

  • completed ≠ fixed。GitHub 的 state_reason 由执行关闭的人选择；重复、过时、已实现都可能标成 completed。本文用它作“非行政性关闭”的代理，不做“修复质量”结论。
  • 每档中位时长最多取 100 条（按创建时间倒序），S 档只有 25 条；数量级可信，小数位不可过度解读。
  • 标签存量计数是全库、全时段的；窗口表只统计 2026-08-12 之后创建的 issue。两者不可相加。
  • 关闭者统计为全量口径：窗口内 13,025 个已关闭 issue 为基线计数，逐条采集覆盖 13,028 条已关闭记录（期间新增 3 条），其中 13,024 条解析到最后一次 ClosedEvent，4 条无法解析。机器人按 GitHub Bot 类型账号计；roboclaw-bot 等 User 类型自动化账号未计入。
  • close:* 不属于 ClawSweeper。多数标签描述指向 claw-marshal；本报告只把它计入“其他自动化”，没有分析其触发条件。
