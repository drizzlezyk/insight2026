没有 bot 时：维护者读代码 → 打标 → review → 作者改 → 合入，4 个人工步骤全包。上面的 6 条路径把维护者动作压缩到 1 次合并、1 条命令或 1 次 proof 复核；⑥ 是唯一仍以人为瓶颈的路径。

二、作者类型：先定义 5 类，再看分布

不用 GitHub 的 author_association 直接分（它会把 steipete 标成 CONTRIBUTOR）。这里用行为定义：有没有合入权、是不是官方名单、是不是机器人。

  • 核心五人组：steipete、vincentkoc、RomneyDa、obviyus、shakkernerd。
  • 其他官方维护者：openclaw.org/people 的 Foundation + Core Maintainers，去掉核心五人组。
  • 名单外有合入权限者：用同仓库分支，或在本窗口内实际执行过 merge，但不在官方名单。
  • 外部贡献者：fork 提交、无合入权限、也不在名单。
  • 机器人：-bot / [bot] / clawsweeper、roboclaw-bot、openclaw-mantis 等；单列，不混入人类分母。
判断顺序机器人 → 核心五人组 → 官方名单 → 同仓库/执行过 merge → 外部

“有合入权限”用行为代理：同仓库 head 分支，或在本窗口内至少 merge 过 1 个 PR。比 author_association 更接近实际权限。

三、proof 等级：外部 PR 的证据更“齐全”吗？

把 proof 标签压成 4 档：L0 无证据 / L1 已提供 / L2 bot 认可（sufficient）/ L3 认可 + 媒体（截图或视频）。override 单列。

这里的 L0–L3 是本报告定义的 proof 完整度分级，不是仓库里的 P0–P3 标签——仓库的 P0–P3 是 impact/priority，和 proof 无关。

已合并的外部 PR 里 73.7% 拿到 proof sufficient（L2）；内部 PR 则 75.1% 是 L0（没有 proof 标签）。proof 首先是外部 PR 的准入条件；内部作者靠自合，不需要它。

L0 里也包含仍带 status: 📣 needs proof 但最终被合并的 PR；proof 标签是终态快照，不等于「合并那一刻的状态」。

六、结论：外部 PR 的 proof 越齐全，合入越快吗？

没有明显关系：外部 L0 36.8 h / L2 33.8 h / L3 39.8 h；Spearman -0.03（n=3,211）。proof 等级不是合并速度的主因。

外部 PR 的 ≤24h 合并率：L0 40.5% → L2 46.2% → L3 43.9%。内部 PR 反而越往高 proof 走越慢（L0 54 min → L3 2.5 h），但绝对时长仍在小时级——内部作者本来就能自合，proof 不是通行证。

分尺寸看，只有 XS 外部 PR 呈同向：L0 45.4 h → L3 6.1 h；S/M/L 没有稳定关系，XL 样本太小，不能外推。

先把两个问题分开：proof 对「会不会被合」的证据更强。全量标签口径（2026-11-16 快照）下，needs proof 合并率 25.2%，proof: sufficient 72.4%，status: ready for maintainer look 85.5%；proof: supplied 只有 33.3%。本页的速度只在「已合并」样本内比较，没合并的 PR 根本不在分母——存在生存偏差。

三个不要过度解读：

  • proof 是结果，不是随机分配。 简单、低风险的 PR 更容易拿到 sufficient；复杂 PR 才需要截图/视频，也更慢。
  • 标签是终态快照。 合并后标签可能被清理或保留；L0 里混有“从没要过 proof”和“要了但没补”的 PR。
  • 总时长包含“等 proof”的时间。 proof 越全可能意味着前面等得越久；它压缩的是“proof 之后到合并”的时间，不是总时长。

更准确的说法：proof 是外部 PR 进入维护者视野的通行证，不是加速器。没有 proof 的外部 PR 大多停在低合并率区间；proof 齐全后，维护者才愿意花那一次合并动作。真正的速度差来自 PR 大小、风险和作者是否已经在维护者信任圈内。

这也是 PPT 第 1 页 ⑥ 的含义：bot 可以清完所有阻塞项，但最终“点合并”仍是人的动作；proof 让这个动作更容易发生，而不是让它消失。

七、口径与数据

窗口：PR 的 merged_at 在 2026-09-11 ~ 2026-11-11（UTC，含端点）。
样本：33,574 个已合并 PR，按编号去重；bot 单列，不进入内部/外部速度对比。
来源：GitHub Search API（REST，逐日分片，避免 1,000 条上限）+ 仓库 labels；作者权限用同仓库 head、窗口内 merge 行为、官方名单三个行为代理。
速度：merged_at - created_at，小时；中位数 / p25 / p75 / p90；≤24h / ≤72h 为占比。
proof 档：L0 无证据；L1 有 supplied 或媒体但未 sufficient；L2 sufficient；L3 sufficient + 截图/视频；override 单列。

已知边界：
① proof 标签是合并后的终态快照，不是事件时间；无法精确拆“等 proof”与“proof 后等合并”。
② 没有控制 PR 的具体 diff 行数、CI 时长、review 轮次；size 标签只是粗代理。
③ 外部/内部的判定依赖“窗口内是否 merge 过”，对低频维护者可能低估内部比例。
④ 描述性统计，不是因果估计；“proof 越全越快”不能读成“补 proof 就能加速”。
