先看结论：它把“维护”拆成了一条可审计的流水线

RoboClaw 的产出不是一个补丁，而是一份可复核的“变更包”：问题、影响、原因、证据、会话、信用、评审、CI、合并回执。人不需要逐行陪跑，但每一个高风险节点都保留了人的否决权。

一句话概括
人类在共享会话里给目标和边界；RoboClaw 在隔离 worktree 里复现、修复、补证；ClawSweeper 给出结构化评审和标签；CI/规则集做硬门禁；最后由 RoboClaw 或人类维护者按精确 head squash 合入，并把人类贡献写进 Co-authored-by。

不是“让机器人随便合”

评审是建议，CI 和安全门禁是硬约束；合并工具会把“评审过的 head”和“实际合入的 head”绑定，head 变了就要重来。

也不是“全自动流水线”

68.4% 的 PR 带共享会话链接，53.7% 明确写“Worked on by”；人类经常在会话里定方向、补环境证据、做最终合入。

真正的加速来自“证据前置”

复现失败→修复通过、精确 head 的 CI、before/after 截图、限制说明都提前写进 PR，评审只需要判断“证据够不够”。

一、它是什么：一个在共享 Gateway 里工作的 maintainer agent

RoboClaw 的 GitHub 账号是 roboclaw-bot，但它的“本体”不是一个 GitHub Action，而是 OpenClaw 多人实例里的 agent roboclaw。它同时拥有会话、工作区、GitHub 身份和合并权限，因此才能从“讨论”一路走到“合入”。

它和“CI 机器人”的关键区别

  • CI 机器人执行固定规则：打标、跑测试、贴评论；不读业务语义，不写产品代码。
  • ClawSweeper是评审 bot：读 diff、给结构化评审、建议标签；但 repair/automerge 命令已退役，它不负责合入。Barnacle 则负责固定规则的路由/关闭（空 body、无证据、作者 open PR 过多等），两者都不替代 maintainer 判断。
  • RoboClaw是完整 agent：能读 owner/callers/tests/history，能改代码、补测试、做截图证据、回应评审、执行合并。它受 maintainer skill 和仓库 AGENTS.md 约束。

三层归因，让“谁做的”可追溯

  • Creator（不可变）：谁创建了会话。
  • Owner（可指派）：当前谁负责跟进，类似 issue assignee。
  • Participants（历史）：实际发过指令、steer 过 turn 的人。

这三层会进入 PR 的 Work sessions、Worked on by 和 merge commit 的 Co-authored-by。归因不是权限，也不能替代评审；但它让“人到底贡献了什么”有迹可循。

二、八段工作流：从任务到合入

这套流程写在 .agents/skills/openclaw-pr-maintainer/SKILL.md 与根 AGENTS.md 里。核心原则是：先证明问题真实存在，再改；先本地证明，再发 PR；评审是建议，门禁是硬约束；合入必须绑定精确 head。

01 · INTAKE
接任务点名 / issue / 队列发现；先看 assignee 和当前状态。
→
02 · INSPECT
读源与复现owner、callers、siblings、tests、history、current main；真实入口复现。
→
03 · ISOLATE
隔离工作区managed worktree / branch；不在共享 checkout 上乱切。
→
04 · IMPLEMENT
修复与本地证明改 owner invariant；红→绿回归；affected siblings；截图/视频。
→
05 · REVIEW
本地评审local ClawSweeper / autoreview；review.json 记录 verdict。
→
06 · PUBLISH
发布 PR结构化 body；draft → ready；保留人类信用。
→
07 · GATES
托管评审与 CIClawSweeper 评审/标签；exact-head CI、安全、CodeQL。
→
08 · LAND
合并与收尾squash 锁定 head；评论回执；清理 worktree。
阶段关键动作产物 / 门禁失败或不确定时
01 接任务
维护者 / agent		 读当前 item、assignee、标签、相关 issue/PR；判断 scope 是 review-only、fix-only、land 还是队列发现。重活开始前先处理 assignment，避免抢别人正在做的单。 明确的任务边界；知道谁是 owner；决定是否需要新 worktree。 另一人 6 小时内已 assign → 不抢；只读请求不做写操作；不确定就停下问。
02 读源与复现
RoboClaw		 读完整模块、owner、callers、siblings、tests、git history、current main；先跑真实失败入口，确认 bug 的前提。不能命名“bug 在哪一行”就不算验证过前提。 可复现的失败；理解 owner invariant；知道哪些是受影响 surface。 已经修过 → 找 canonical fix + 证明；无法复现 → 记录缺口，不 speculative fix。
03 隔离工作区
Gateway + git		 在任务专属 worktree/branch 工作；复用已有 base，不反复 clone；保留无关改动，不切换别人正在用的 checkout。 干净的 branch、可复现的 base、明确的 artifact 目录。 路径/权限不对 → 先做 workspace preflight；不绕过 guard。
04 修复与本地证明
RoboClaw		 修 owning invariant；加 1–2 个失败于 base、通过于修复的回归；跑 affected consumers；UI 变更做 before/after 截图；按需跑 e2e / 真实 Gateway。 红→绿证明；测试/类型/lint/format；视觉证据；限制说明；pr-simplify 过的 diff。 测试失败 → 先判断是产品缺陷还是测试问题；不掩盖、不把“重跑通过”当修复。
05 本地评审
RoboClaw		 维护者路径：local ClawSweeper 评审最终 committed range；不可用时 local autoreview；完成后才请求 hosted review。填 review.json verdict。 review-init / review-validate-artifacts 通过；找到的 P0–P2 已处理或有一行拒绝理由。 评审超时 → 继续已授权工作；substantive change → 重新 review，而不是只 rebase。
06 发布 PR
RoboClaw		 先 draft；body 用当前模板：What Problem This Solves / User Impact / Why This Change Was Made / Evidence；补 Work sessions、Worked on by、Contributor credit；保留 maintainer edits。 可读的 PR body；精确 head；draft → ready；CI 已挂到 pushed head。 mergeable 为空 → 等；CI 没挂上 → hourly sweeper 或授权 close/reopen。
07 托管评审与 CI
ClawSweeper + CI		 ClawSweeper 队列评审：读 diff、给 verdict、评分、findings、label justification；确定性 workflow 打标签。CI 跑 openclaw/ci-gate、安全、CodeQL、包验收等。 评审评论 + 标签状态机；exact-head 绿；必需评审/安全审批；失败分类。 PR 导致的失败 → 修；继承性失败 → 走带证据的 exception；绝不为“变绿”盲目 rerun。
08 合并与收尾
native tooling		 prepare-run 绑定 head；merge-run --auto-merge 提交 pinned squash；watcher 每 2–3 分钟看 head/checks/mergeability；验证远端 merge + ancestry。 “Merged via squash”回执：prepared head + landed commit；main 上带人类 co-author；worktree/日志清理。 head 变了 → 重新 review/prepare/CI；不确定写 → 先 reconcile，不盲重试。

合并阶段的“原生命令链”

这不是 RoboClaw 自己发明的流程，而是仓库维护者 skill 里的原生路径；agent 只是按它执行。关键点是 review.json 绑定评审、prepare-run 绑定 pending gates、merge-run 提交 pinned squash。

scripts/pr review-init <pr>
scripts/pr review-checkout-main <pr>
scripts/pr review-checkout-pr <pr>
scripts/pr review-artifacts-init <pr>
# 完成 .local/review.json（verdict 绑定 exact head）
scripts/pr review-validate-artifacts <pr>

env -u OPENCLAW_TESTBOX OPENCLAW_PR_GATES_REMOTE=github scripts/pr prepare-run <pr>
scripts/pr merge-run <pr> --auto-merge

合并前必须满足：openclaw/ci-gate + 适用的安全评审 + required reviews；auto-merge 被接受不等于完成，仍要验证远端 merge 和 main ancestry。

一段真实的 Evidence 长什么样

“Final tested head: fb7c592…. The full 289-test Wear suite was rerun on this exact head… Full Wear unit suite: 289 passed, 0 failed, 0 skipped. Exact-head GitHub CI run: passed… Screenshots below are inspected native-graphics Robolectric captures of the real app… No connected Android device was available; physical-watch acceptance was not run.” — PR #151224，Wear OS 修复的 Evidence 段（节选）
  • 先给结论：哪个 head、跑了什么、结果如何。
  • 再给反证：原实现上失败、修复后通过；不是只贴“测试通过”。
  • 再给限制：没有真机、没有跑哪些环境，明确写出来。
  • 最后给闭环：exact-head CI run 链接，评审/CI 可以对齐同一个 SHA。

标签不是装饰，是一台“状态机”

六、人机协作与信用：机器人干活，人类留名

RoboClaw 的“自动化”不是把人排除在外，而是把人的贡献从“陪跑”变成“可记录的判断与证据”。这套信用机制有三条线：会话链接、PR 正文的 Worked on by、以及 merge commit 的 Co-authored-by。

① Work sessions

68.4% 的 PR 带 team.openclaw.ai/chat/roboclaw/dashboard/… 链接。评审可以直接打开产生这个 diff 的会话，看到任务、讨论、测试和发布过程。

② Worked on by

53.7% 的 PR 明确写“Worked on by: @human”。样本里出现 12 个不同的协作者账号；最高的 IWhatsskill 出现 40 次，其次是 steipete 17 次、brokemac79 12 次。

③ Co-authored-by

merge commit 保留人类 co-author。比如 #185963 的 squash commit 同时写入了 etzelm 与 Patrick-Erichsen；机器身份 services+roboclaw@openclaw.org 与人类信用分开。

为什么这套信用重要

  • 不是“机器人抢功”：merge commit 明确区分机器身份与人类 co-author；贡献者的原始 patch/ancestry 在替换时也要保留。
  • 不是“人类挂名”：Co-authored-by 来自会话里的真实参与者、已验证的 GitHub 身份和贡献快照，不是随便写一个名字。
  • 可审计：会话链接、PR body、commit trailer 三处互相印证；评审可以追溯“这个判断是谁做的”。
“Contributor credit: @etzelm reported, investigated and implemented the original per-document fix. Source ancestry and prior publication credit are preserved.” — #185963 的 merge commit message（节选）

仓库规则还明确：不使用“agent 自夸式”的 attribution trailer；机器身份由 commit author 表示，人类信用由 Co-authored-by 表示。

七、控制机制与风险：哪些是硬的，哪些是软的

这套工作流最重要的设计不是“让 agent 更快”，而是“让 agent 的快不越过人的判断”。但它也有真实的张力：自合比例、评审延迟、标签漂移、规模重尾。

硬约束（不靠 agent 自觉）

Exact-head CI + ci-gate

合并请求绑定 prepared head；CI、安全评审、required reviews 是 GitHub 规则集层面的门禁。head 变了就要重新评审/准备。

Pinned squash + merge 回执

“Merged via squash”评论记录 prepared head 与 landed commit；可以核对“评审的是不是合入的那个”。

安全敏感路径 guard

改动 auth/pairing/permission 等路径会触发 informational guard；是否有 secops 审批取决于作者角色与路径策略，不是 agent 自判。

评审与合并分离

ClawSweeper 只给评审/标签建议，不执行 repair/automerge；RoboClaw 即使有 maintain 权限，也要过规则集和必需评审。

关闭也要证据

superseded / already-fixed 的关闭必须给出 canonical fix、替代 PR 或当前 main 的证明；不是“机器人觉得不需要”。

软约束（依赖流程与判断）

自合比例高

78.1% 的已合 PR 由 RoboClaw 自己按下合并。虽然评审/CI 是独立的，但“作者 = 合并者”仍然是一个治理张力；后期人类合入占比升到 48.9%，可能反映了团队对最终签核的调整。

评审延迟与长尾

中位 67.6 分钟，但 p90 是 26.1 小时；521 个 PR 仍开放，中位年龄 9.9 天、p90 50.5 天。复杂 PR 的评审/证据成本远高于小修。

标签/自动化漂移

真实案例里出现过 ClawSweeper 说“已加标签”但标签未同步、intake 暂时不可用；所以不能把标签当作唯一真相，仍要看评审正文和 CI。

吞吐量 > 评审容量

11-03 单日新开 217 个，但当天只合入 117 个；峰值之后会留下排队。高吞吐并不等于即时吞吐。

大 PR 的合入率明显更低

XL 只有 64.5%，L 76.2%，而 XS/S 约 82%。这不是说大 PR 不该做，而是它们需要更多人审、更多证据和更长窗口。

最值得盯的两个指标：① 自合 PR 的中位合入时间（45 分钟）vs 人类合入（9.5 小时）——差距说明人类确认是主要慢路径；② 开放 PR 的年龄分布（p90 50.5 天）——它比“平均合入时间”更能暴露评审/证据瓶颈。

八、如果你想复刻：最小可运行清单

RoboClaw 的模式不依赖某个神奇模型，而依赖“共享会话 + 隔离工作区 + 证据模板 + 独立评审 + 精确 head 门禁 + 信用机制”这六件套。下面是可以按顺序落地的清单。

平台侧

  • 一个共享 Gateway：人类和 agent 在同一个会话里工作，有 creator/owner/participant 归因与 presence。
  • 每任务一个 worktree：agent 有独立 branch/checkout，不污染共享工作区；会话里能直接看 diff。
  • GitHub 身份与权限分离：机器人账号有 write/merge，但分支规则集、required reviews、CI gate 独立于 agent。
  • 会话 → PR 的回链：发布时自动写入 Work sessions；支持人类 co-author 信用。

流程侧

  • 一份 maintainer skill：写清 authority、scope、复现、proof、review route、landing、closeout；根 AGENTS.md 保持短。
  • 一份 PR 模板：Problem / Impact / Why / Evidence 四段；Evidence 必须含 exact head、红→绿、CI、限制。
  • 一个独立评审 bot：结构化 verdict + 评分 + findings + label justification；默认 advisory，不直接合并。
  • 精确 head 合并工具：review.json 绑定 head；prepare 绑定 gates；merge 提交 pinned squash；自动回执。
  • 标签状态机：intake / size / priority / rating / proof / merge-risk / status；status 明确“下一步谁动”。
  • 关闭与清理规则：superseded 要写替代 PR；already-fixed 要写 canonical fix；worktree/日志按 closeout 清理。
读一个 RoboClaw PR 的最短路径：先看 status 判断下一步在谁；再看 rating + proof 判断证据强度；然后读 Evidence 段的 exact head / 红→绿 / CI；最后看 merge 回执的 prepared head 与 landed commit 是否一致。评论区很长时，优先读 ClawSweeper 的 “Merge readiness”“Before merge” 和 “Labels” 三节。

数据源

  • PR 主数据集：roboclaw-prs-20260911-20261118.json，4,082 条；字段：number/title/url/body/state/createdAt/mergedAt/labels。由 GitHub API 检索得到（author:roboclaw-bot，2026-09-11 ~ 11-18）。

  • 评论抽样：44 个 PR 的 issue comments / reviews，用于回执延迟、复审次数、人类评论率；另抽 10 个关闭 PR 判断关闭原因。
  • 流程文档：仓库根 AGENTS.md、openclaw-pr-maintainer/SKILL.md 及 landing/triage 参考、clawsweeper/SKILL.md、PR review flow、Multiplayer、PR 模板。
  • 真实 PR：#198457、#151216、#185963、#150896、#151079 的 body、comments、reviews、commits、merge commit。

口径与限制

  • 时间：全部按 UTC；合入耗时 = mergedAt - createdAt，不是“首次评审耗时”。
  • 标签是抓取时点快照：不是历史状态；一个 PR 可能后来被重新打标，因此“合入率”是当前标签下的相关性，不是因果。
  • merged_by 是最终动作：不代表谁做了评审或谁写了代码；人类合入也可能只是最后按按钮。
  • 评论抽样不是全量：44 个 PR 的复审/评论比例用于描述机制，不应外推为全量精确比例。
  • “Worked on by”是正文声明：只统计显式提及，实际会话参与者可能更多；Co-authored-by 才是 commit 级信用。
  • 数据窗口：2026-09-11 ~ 11-18；11-18 是抓取日，最后一天数据不完整。

本报告是流程分析，不是对 RoboClaw 的绩效评价。它想回答的问题是：一个被授予 maintain 权限的 agent，如何把“读问题—改代码—补证据—过评审—合入—留信用”变成一条可重复、可审计的流水线。
