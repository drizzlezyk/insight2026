一、先定位：它不是 PR review bot

Mantis 在 PR 上有两重身份，但都不做“评审别人代码、决定 merge/close”这件事。

① 在 PR 上：QA / evidence bot

被 @ 才动；产出是评论里的证据

维护者在 PR 评论里发 @openclaw-mantis + 请求模式，它跑可复现的 QA 场景，把 baseline vs candidate 的截图、视频链接和运行信息贴回 PR。触发必须是 PR 评论；普通 issue 评论会直接失败。

② 在 PR 外：自动化 PR 作者

自己开 PR，自己合并 routine 变更

它持续生成 locale / i18n / CI timing 这类维护 PR，通过可评审的 automation branch 发布，不绕过 protected-branch checks；例行变更在 checks 通过后自动合并。

它不做什么：不 review 别人的 PR，不判断代码质量，不决定 close/merge 语义。ClawSweeper 负责评审/关闭；Mantis 负责 QA 证据和 routine PR。它“针对 PR”，但不是“PR 评审 bot”。

核心是 mantis-resolve-request.yml：从 PR 评论里解析请求，跑场景，再把 evidence 挂回同一个 PR。

mantis-resolve-request.yml：“Mantis issue_comment trigger requires a pull request comment.” 这是它“只针对 PR”的最直接证据。

可跑的场景

  • discord-status-reactions-tool-only
  • discord-thread-reply-filepath-attachment
  • slack-desktop-smoke
  • web-ui-chat-proof
  • telegram-bot-e2e-proof

触发时加 👀 reaction；结束后由 mantis-clear-reaction.yml 清掉。请求者看到的“结果”是 PR 评论，不是 issue 回复。

视频：给链接

通知的细节：评论由 openclaw-mantis[bot] 发在 PR 上，模板里有 Trigger: issue_comment，但没有显式 @请求者；通知来自 PR 评论本身。它用 marker（如 <!-- mantis-discord-status-reactions -->）做 upsert：已有评论就 PATCH，没有才新建。好处是不刷屏；代价是 PATCH 旧评论不一定像新评论那样再次触发通知——需要明确提醒时，要加 @mention 或发新评论。

五、对 vllm-ascend 的启示

Mantis 值得借的是“PR 上的可复现证据 + bot PR 的独立 lane”；不值得借的是无批量的 routine PR 噪音。

BORROW 01

QA evidence 挂回 PR

把可复现的 baseline/candidate 证据贴回 PR，维护者不用自己跑；失败也发，Overall 标 fail / blocked。

BORROW 02

bot PR 仍走 PR 门

automation PR 也要过 checks、带 size / risk / status 标签；不做直推，保留可回滚和可审计。

AVOID 03

routine PR 噪音

locale refresh 一天多个会稀释 review 队列；应该 batch/coalesce，或给 automation lane 明确的 auto-merge 范围和配额。

一句话：Mantis 证明了“QA 证据可以产品化”，也暴露了“bot PR 需要独立车道”。对 vllm-ascend：先把 PR 的 evidence 和 label/ready 门做出来，再谈 bot 自动化；不要把 bot PR 和人类 PR 混在同一个 review 队列里。
