ClawSweeper 处理 Issue 的全流程泳道图

三条泳道：用户 / 贡献者、ClawSweeper 系统、维护者。系统全程只「提议」，写操作集中在 Apply 通道并再次校验实时状态；用户与维护者各有明确、可预期的交互点。

全流程

从「用户提 issue」到「关闭或复活」

  • AI 判断（Codex，只读）
  • 受护栏约束的执行 / 提议
  • 保留与复活（安全出口）
  • 确定性状态 / 跨角色交互

交互点汇总

对用户 / 对维护者分别意味着什么

对用户 / 贡献者

  • 提 issue 即触发：打开、编辑或评论都会经 dispatcher 驱动一次审查，无需手动 @ 机器人。
  • 拿到实质反馈：每项获得一条耐久审查评论（原地编辑、不刷屏），可能是「需要更多信息」「疑似重复」「已在 main 实现」等结论与理由。
  • 补充信息可再触发：编辑正文或评论会形成新的审查意图（队列合并为最新一次）。
  • 误关可自助复活：一条评论即可，无需维护者介入。
  • 可预期性：被 Fixes #123 引用、或与同作者 PR 配对的 issue，在 PR 合并/关闭前不会被关。

对维护者

  • 四个命令：@clawsweeper review（全新只读审查）、re-review（变更后带新证据重审）、explain（解释结论）、stop（终止后续自动处理）。
  • 决策包：需要人裁决时给出结构化 JSON——问题、理由、选项、建议、可能负责人。
  • 默认受保护：维护者署名的 issue 保持开放（除非能验证 main 已实现）；受保护标签与配对关系同样拦截关闭。
  • 豁免手段：用标签（如 size: accepted-large）放行特殊情形或阻止提议。
  • 人工裁决回灌：采纳关闭 / 保留观察的选择会作为输入影响 Apply 通道；stop（虚线）直接切断后续处理。
  • 完全可审计：每个动作都带可读理由，行动写入只增账本。
