先纠正一个前提

这不是传统开源仓库

核心 CLI 闭源（LICENSE.md 保留所有权利 + 商业条款），仓库里主要是文档、CHANGELOG、issue 追踪、社区自动化 workflow，以及 1,852 个 mod 文件 / plugins。真正的社区入口是反馈（issue）和扩展（plugins / mods / slash 命令），而不是向核心提交代码。88k 个 closed issue vs 693 个 closed PR——反馈是代码贡献的 127 倍。

P1.1

14 个 workflow 的能力清单

传统治理文件（CONTRIBUTING / CODE_OF_CONDUCT / CODEOWNERS / dependabot）全部缺席，取而代之的是一套「AI agent + 强制 CI 护栏」。

P1.2

issue 处理的完整流程

三条并行轨道：AI 分诊（打标签、不评论）、AI 去重（5 agent 找重复）、生命周期（超时自动关 → 锁定）。用户可 @claude 召唤 AI，但实测该通道只读、无回帖（见 P1.4）。

生命周期计时（唯一真源 issue-lifecycle.ts）

invalid · 3d
needs-repro / needs-info · 7d
stale / autoclose · 14d
lock · +7d

👍 ≥ 10 的 issue 不标 stale；真人新评论会撤销 autoclose。

关键机制

  • 模板引导 + 空白禁用：6 个结构化模板，config.yml 关闭空白 issue，优先导流到 Discord / 文档；bug 模板强制 claude --version、平台、OS、终端等字段，为 AI 分诊提供结构化输入。
  • AI 分诊：只打标签、永不评论；分类标签五选一；「是否关于 Claude Code」靠 body 里的信号（CLAUDE.md、.claude/、MCP 等）判断，否则打 invalid。
  • AI 去重：独立于分诊，5 个并行 agent 用不同搜索策略找重复，过滤 agent 剔误报，最多评论 3 个候选。
  • 闭环终点：关闭 7 天后锁定，防止已解决帖子被反复灌水。
  • 安全护栏：所有调用 Claude 的 job 跑在 egress 白名单防火墙；--permission-mode auto + --disallowedTools WebFetch,WebSearch,Write,Edit；workflow-hardening 强制这些配置不可退化。

P1.4 深入

@claude 在问什么、有没有回答、打标后谁接

用户 @claude 一般在问什么

搜 mentions:claude（@claude 是真实 GitHub 用户 id=81847）命中 447 个 issue。抽样归纳：一半是「催办 / 求关注」，一半是「把 AI 当随时可叫的协作者」。

issue请求类型原文摘录
#105607求修复 / 求关注「Please fix this, having a lot of issue lately due to this. @claude」
#102056请求实现功能「@claude could we do that?」
#97842给方案让 AI 干活「…The fix is to build the squash commit only from the existing committed tree…」
#96043催更 / 问进展「any update @claude」
#94532申诉误标「@claude I don't think this is an invalid report.」

Claude 真的正常回答了吗？——基本没有

抽样 20 例，「正常回答」0 / 20：16 例 @claude 后无任何 AI 回帖，1 例误触发查重，3 例有 bot 动作但是误判。

根因是机制性的，不是模型不行：claude.yml 的 @claude job 是只读的——permissions: issues: read、不传 token、不传 prompt，Claude 被拉起但没有回帖通道。用户看到的 bot 行为几乎都来自 claude-issue-triage（打标 / 误关）和 claude-dedupe-issues（查重）。

失败模式从高到低：沉默（@claude 无回应，用户往往同时 @ 真人兜底）> 误判（#94532 把真 bug 标 invalid 并摘掉 bug 标签，用户追问无解释）> 查重代替回答。

沉默的典型：#105607、#102056、#97842、#96043、#93287 等 16 例 @claude 后无任何 AI 回帖；误判的实锤是 #94532——用户标 bug 后 1 分钟 bot 加 invalid 并摘掉 bug 标签，用户追问「Why is this marked invalid?」无解释。

局限：20 / 447 非随机样本；「哪条评论是 AI 发的」靠措辞与签名 + 配置推断（@claude 工作流本身从未产出可见回帖）；无法区分 @claude job 是「静默成功但无写通道」还是「运行报错」——根因来自配置推断；只看 issue，未看 PR。

打标之后怎么分配？——AI 只打标，不分配

triage-issue.md 明文「Your only actions are adding or removing labels」；脚本只接受 --add-label / --remove-label；sweep.ts 会跳过「已被指派」的 issue——反证指派是人工动作。仓库没有任何自动 assignee 机制，40 个 area:* 标签只提供「归类信号」，靠维护者按标签认领。

可借鉴的自动分配方案（Claude Code 自己没做）：

  • labeled 事件 + 标签→负责人映射：打上 area:foo 时执行 gh issue edit --add-assignee @owner，成本最低。
  • Probot auto-assign / kentaro-m/auto-assign-action：按标签 / 作者 / 轮转自动指派。
  • area:* → CODEOWNERS / team：注意 CODEOWNERS 只管 PR review，不管 issue 指派。

可能得到的结论

AI 时代开源社区入口变化的 6 条洞察

01 · 入口对话化

入口从「单一 issue 表单」变成「对话优先 + 结构化兜底」：空白 issue 禁用、优先导流 Discord，bug 模板预埋结构化字段供 AI 消费。

证据：config.yml、issue 模板
02 · AI 承接 triage

分诊、去重、生命周期管理——传统上最耗 maintainer 的重复劳动，全部交给 AI，且设计为保守策略（只打标签、宁缺毋滥）。

证据：triage / dedupe / sweep 等 9 个 workflow
03 · 治理转向护栏 + CI

治理重心从「人治规范文档」转向「agent 安全护栏 + 强制 CI」，传统的 CONTRIBUTING / CODE_OF_CONDUCT / CODEOWNERS 全部缺席。

证据：workflow-hardening、egress-firewall、CLAUDE.md
04 · 反馈数据化

issue 打开 / 重复事件进 Statsig，打开即镜像到内部系统——反馈不再是「帖子」，而是可度量、可关联的产品数据。

证据：log-issue-events、issue-opened-dispatch
05 · 贡献转向扩展

贡献入口从「改核心代码」迁到「插件 / mods / slash 命令」：88k closed issues vs 693 PR，但扩展生态开放且带自动测试。

证据：LICENSE.md、mod-tests、1,852 个 mod 文件
06 · AI 成为社区成员（设计 vs 现实）

设计意图是用户 @claude 即得即时 AI 响应；但实测该 job 只读（issues: read、无 token、无 prompt），没有回帖通道——抽样 20 例「正常回答」0 例。AI 确实在社区里动了，但形态是「会打标、会误关、不会答话」。

证据：claude.yml 配置、20 例 @claude 回复质量抽样
给「拥有开源社区的部门」的自检清单
  1. 反馈入口是否结构化到「机器可消费」？
  2. 分诊 / 去重 / 生命周期是否可交给 AI 并配安全护栏？
  3. 反馈是否进了数据管道（可度量、可关联）？
  4. 社区贡献是否从「改核心」转向「做扩展」？
  5. 传统治理文档是否需要被「AI 可执行规范 + 强制 CI」部分取代？
