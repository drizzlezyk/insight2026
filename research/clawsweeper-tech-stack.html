01 · 技术栈

刻意保持简单的工具链

整个系统是一个 纯 TypeScript / Node 单体 CLI（dist/clawsweeper.js），配一个 Cloudflare Worker 控制面。没有数据库、没有队列中间件、没有 Web 框架——容量与并发全部交给 Cloudflare Durable Object，编排全部交给 GitHub Actions。

03 · GitHub Actions 全流程（重点）

Actions 只做 5 件事，路由逻辑全在 TypeScript

硬性架构约束：workflow 只负责 环境准备、铸凭据、跑脚本、上传产物、发布状态。所有的路由规则必须写在 TypeScript 里——这样 webhook 接入、repository_dispatch 回退、手动触发、定时任务走同一套行为。workflow 里不写业务 YAML/bash。

三类触发器

  • schedule（cron）：定时扫描/回填/执行，见下方时间表。
  • repository_dispatch：目标仓库事件或扇出派发单条审查（clawsweeper_target_sweep 等 action 类型）。
  • workflow_dispatch：人工运维（指定 item_number / 重跑 / 回填 / apply_existing）。

10 个复合 action（组合式步骤）

把重复的「准备」抽成可复用 action，workflow 里只引用它们：

  • setup-pnpm、setup-state（稀疏检出运维状态）、setup-action-ledger（账本）
  • create-state-token、create-target-write-token（按最小权限铸造 GitHub App token）
  • setup-codex、setup-openclaw、setup-openclaw-codex-source（安装/缓存模型执行器）
  • setup-review-tools（审查工具链）、setup-github-egress-observer（出网遥测）

权限与凭据模型

  • 最小权限：workflow 显式声明 contents/actions/issues/pull-requests: write；审查 job 只读（checks/contents/issues/pull-requests/statuses: read）。
  • GitHub App token：用 actions/create-github-app-token 按 owner/repo 粒度铸造，读 token 与写 token 分离（create-target-write-token 单独控制）。
  • 公开发布的 App client id：Iv23liOECG0slfuhz093（私钥走 secret，不进仓库）。
  • 控制面签名：control-plane-curl.sh 只在这里计算 x-clawsweeper-exact-review-signature＝sha256= + 以 CLAWSWEEPER_WEBHOOK_SECRET 为密钥、对 body 精确字节做 HMAC-SHA256。
  • 重试语义：连接失败/HTTP 5xx 最多 6 次尝试、总退避 ≤62 秒（2/4/8/16/32 秒，尊重 Retry-After 上限 60 秒），足以覆盖 Worker 部署/DO 重置的 15–30 秒抖动窗口；4xx 不重试。
  • concurrency：按「目标仓库 + 租约」分组，cancel-in-progress: false，避免重复/竞态。

04 · 队列与容量

并发不是靠 Actions 信号量，而是靠 Durable Object 队列

精确审查的准入由 Worker 里的 ExactReviewQueue 决定：它按「仓库 + item 编号」合并投递（新 webhook 只更新最新意图，不额外消耗 runner），并用租约、回收、去抖与限流控制并发。容量参数集中在 config/automation-limits.json。

参数值含义
workers.max128全局 Codex 并发预算（唯一主旋钮）
workers.reserve_for_interactive16后台通道为精确/手动/紧急工作预留的槽位
workers.expansion_reserve8为独立规划的矩阵扩展预留
EXACT_REVIEW_QUEUE_MAX_CONCURRENT80同时派发的精确审查上限
EXACT_REVIEW_TARGET_MAX_CONCURRENT64单个目标仓库可占用的上限（给其他仓库留 16 槽）
EXACT_REVIEW_ACTIONS_BUDGET194独立的 Actions 预算，保证发布不被审查挤到 0
EXACT_REVIEW_SCHEDULED_MAX_CONCURRENT32定时热接入 + 常规回填合计上限
派生上限89 / 38 / 44常规审查 70%、常规活跃下限 30%、热接入 35%（相对 128）
入门静默窗10 分钟普通 PR 需 head/title/body/draft 稳定 10 分钟才审

背压分级（自动降速）

级别触发条件后台预算
none未达软阈值正常动态预算
soft≥150 待处理 或 最老待处理 ≥30 分钟ceil(正常预算 × 0.5)
hard≥400 待处理 或 最老待处理 ≥2 小时max(1, floor(正常预算 × 0.1))

阈值可由仓库变量覆盖：CLAWSWEEPER_QUEUE_PRESSURE_SOFT_PENDING(150)、..._HARD_PENDING(400)、..._SOFT_AGE_MS(1800000)、..._HARD_AGE_MS(7200000)。

三个明确的状态所有者

逻辑路径规范所有者

可回滚的存储演进：状态 JSON 在「信封压缩」后更小；但代码明确要求 部署支持解压的 Worker 之后才允许写压缩格式，并把「已部署的可解码 SHA」作为回滚下限——历史压缩必须用 exact-review-queue-maintenance.yml 分页、可断点、可审计地手动执行。

06 · 模型执行层

Codex 只读审查是怎么跑起来的

  • 一次审查 = 一个 Codex 进程；Codex 自己负责请求与流恢复，ClawSweeper 只保留最终错误分类，由队列决定是否发起新的一次审查。
  • 模型与档位：gpt-6.1-sol，medium reasoning；直接 API 认证模式（login / proxy）走该模型，clawrouter 模式走其私有推理别名。
  • 优先服务：由 OWNER/MEMBER/COLLABORATOR 撰写，或实时权限为 write/maintain/admin 的条目走 priority（快）服务；其余走 standard。
  • 输入扫描（agent-input-scan.ts）：拒绝不安全内容，输出终止性原因（scanner_unavailable、findings、deadline、unsafe_path 等）；scanner_refused 会保留队列项并阻止自动释放。
  • 安全信号（security-signals.ts）：在提示压缩前检查原始正文与讨论，识别远程 shell 替换、下载即执行、编码环境变量泄漏等；命中即升级为需要人工审核的安全项，并阻止一切自动关闭。
  • 提示组装：按 repositoryProfileFor(item.repo) 选中配置档，渲染出 Repository Policy 段，并按其 apply_close_rules 裁剪可用的关闭理由。

必须保持确定性、不得交给模型的清单：维护者/写权限判定 · 目标仓库准入边界 · 受保护标签与维护者署名关闭护栏 · 陈旧漂移与精确 head 身份 · worker 预算强制 · 最终评论/标签/关闭动作。Codex 只「提议处置」，由确定性代码决定该变更是否被允许并执行。

07 · 落地到你的社区

如果你想引入，需要准备什么

基础设施前置

  • Cloudflare 账号：Worker + Durable Object（ExactReviewQueue，SQLite 后端）+ 一个 R2 bucket。
  • GitHub App：client id + 私钥；订阅 Issues / Pull requests / Issue comments webhook；按最小权限授予 contents/issues/pull-requests 读写。
  • 一个 state 仓库（如 <org>/clawsweeper-state），含 state 分支。
  • 模型执行凭据：用 openclaw runner 时需 OpenAI/Anthropic/Gemini/Kimi/OpenRouter 等 provider key；用 codex runner 走内部服务。
  • 自托管：官方实例不对外提供免费审查——fork 后部署到你自己的组织。

需要改的配置

  • config/automation-limits.json — 全局并发预算（workers.max）
  • config/target-repositories.json — 目标仓库、关闭规则、promptNote
  • src/repository-profiles.ts — 内置配置档与 apply_close_rules
  • dashboard/wrangler.toml — TARGET_REPOS / APPLY_TARGET_REPOS / 公开看板白名单
  • Actions 仓库变量/密钥 — App 私钥、CLAWSWEEPER_WEBHOOK_SECRET、队列 URL、各关闭开关

接入一个仓库：官方 6 步

  1. 在目标仓库安装 ClawSweeper GitHub App。
  2. 把 target dispatcher workflow 加进目标仓库并合并（用 OIDC，不需要任何 ClawSweeper 密钥）。
  3. 确认 App 收到 Issues、Pull requests、Issue comments 三类 webhook。
  4. 在目标仓库打开/编辑/评论一个 issue 或 PR，确认出现一次 dispatcher run。
  5. 确认 Worker 直接摄入成功，且队列审查出现在 clawsweeper/actions（不应出现中继 run）。
  6. 确认该条目获得一条耐久审查评论。

建议的渐进上线路径

先观察，再放开关闭。 OpenClaw 自己就是这么推的：① review-only——所有仓库先只审查、全部 apply_close_rules 留空（本地配置档默认关闭规则为空）；② 定点开放——只为明确需要的仓库开 implemented_on_main；③ 按需开关——超大 PR（默认开）、作者 PR 配额、未确认产品方向、陈旧版本 bug 等策略一律默认 off，靠环境变量逐项开启。批量推广用 target-fanout 先小批试跑（--dry-run 先看清单）。

默认开启的关闭策略

  • CLAWSWEEPER_OVERSIZED_PR_CLOSE_ENABLED = true（>50,000 行）
  • CLAWSWEEPER_MAX_PR_CHANGED_LINES = 50000
  • CLAWSWEEPER_AUTO_CLOSE_REASONS = all

默认关闭（需显式开启）

  • 未确认产品方向关闭（product direction）
  • 无赞助功能关闭（unsponsored feature）
  • 陈旧版本 bug / 过时小修 PR 关闭
  • 作者 PR 配额关闭（CLAWSWEEPER_AUTHOR_PR_BUDGET=15，单次最多关 5 个）
