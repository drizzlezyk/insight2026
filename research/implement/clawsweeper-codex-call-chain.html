04为什么要多一层 worker 进程

runCodexProcess 是同步 API，但它并不是直接在调用方进程里 spawn Codex。

runCodexProcess() 做三件事：

  • 创建临时目录 mkdtemp("clawsweeper-codex-process-")，把参数、路径、超时写进 options.json（权限 0600）。
  • 用 spawnSync(process.execPath, [codex-process-worker.js, optionsPath]) 起一个 Node 子进程，把 prompt 作为 input 交给它。
  • worker 结束后读取 result.json，校验大小（64 KiB + 12 × tailBytes），反序列化返回。

这样上层拿到的是一个同步的、有界的、可判定失败的结果对象，而 Codex 的异步生命周期被隔离在 worker 里。

src/codex-process.ts:48–99（节选）
export function runCodexProcess(options: {...}): CodexProcessResult {
  const workDir = mkdtempSync(join(tmpdir(), "clawsweeper-codex-process-"));
  const optionsPath = join(workDir, "options.json");
  const resultPath = join(workDir, "result.json");
  try {
    writeFileSync(optionsPath, JSON.stringify({
      args: [...options.args],
      command: codexProcessCommand(options.env, process.platform, options.cwd),
      timeoutMs: options.timeoutMs,
      resultPath, stdoutPath, stderrPath,
      tailBytes, maxOutputFileBytes,
      ...
    }), { encoding: "utf8", mode: 0o600 });

    const worker = spawnSync(process.execPath, [CODEX_PROCESS_WORKER_PATH, optionsPath], {
      cwd: options.cwd,
      env: options.env,
      input: options.input,                 // prompt → worker stdin
      stdio: ["pipe", "ignore", "ignore"],
      timeout: options.timeoutMs + 10_000,   // worker 的硬兜底
    });
    // …读取 result.json、校验大小、反序列化…
  } finally {
    rmSync(workDir, { recursive: true, force: true });
  }
}
收益：调用方不需要处理 Codex 的流、信号和僵尸进程；worker 即使被强杀，父进程也只看到“没写 result.json”，可安全归类为进程失败，而不会误信被截断的 stderr。

src/codex-spawn.ts:100–123
export function spawnCodex(
  args: readonly string[],
  options: { cwd: string; env: NodeJS.ProcessEnv },
): ChildProcessWithoutNullStreams {
  const invocation = codexSpawnInvocation(args, options.env, process.platform, options.cwd);
  const child = spawn(invocation.command, invocation.args, {
    cwd: options.cwd,
    env: options.env,
    stdio: ["pipe", "pipe", "pipe"],
    detached: process.platform !== "win32",   // POSIX: 独立进程组，便于整组清理
    windowsHide: true,
    ...(invocation.windowsVerbatimArguments ? { windowsVerbatimArguments: true } : {}),
  });
  if (process.platform !== "win32") {
    child.once("exit", () => {
      // 正常退出也要清掉可能仍持有管道的后代进程
      if (!gracefulTerminations.has(child)) signalProcessGroup(child.pid, "SIGKILL");
    });
  }
  return child;
}

src/codex-spawn.ts:61–86
export function terminateCodexProcessTree(child, signal = "SIGTERM", forceAfterMs = 1_000) {
  if (process.platform === "win32") {
    if (child.pid) {
      spawnSync(windowsSystemExecutable("taskkill.exe", process.env),
        ["/pid", String(child.pid), "/t", "/f"], { stdio: "ignore", windowsHide: true });
    }
    return undefined;
  }
  if (signal !== "SIGKILL") gracefulTerminations.add(child);
  signalProcessGroup(child.pid, signal);
  if (signal === "SIGKILL") return undefined;
  const timer = setTimeout(() => signalProcessGroup(child.pid, "SIGKILL"), forceAfterMs);
  timer.unref();
  return timer;
}
平台差异：Windows 用 taskkill /pid <pid> /t /f 整棵树强杀； POSIX 先给进程组发 SIGTERM，1 秒后再 SIGKILL。Codex 自己的子进程（git、ripgrep 等）也随之回收。

07输出捕获与结果文件

输出有两条通道：日志文件流，以及受管结果文件。

7.1 stdout / stderr：有界落盘 + 保留尾部

  • 日志文件最多写 maxOutputFileBytes（默认 128 MiB），超出后截断并保留尾部。
  • 返回给调用方的只有 tailBytes（默认 64 KiB），避免把整段 Codex JSONL 塞进内存。
  • 文件由 codex-output-capture.ts 管理，截断时写入 ...[Codex output truncated; final tail follows]... 标记。

7.2 最终决策：stdout 解析，而不是让 Codex 直接写文件

src/agent-runner.ts:418–422
function managedCodexStdoutArgs(args: readonly string[]): string[] {
  const index = args.lastIndexOf("--output-last-message");
  const withoutFile = index < 0 ? [...args] : [...args.slice(0, index), ...args.slice(index + 2)];
  return withoutFile.filter((arg) => arg !== "--json" && arg !== "--experimental-json");
}

调用方设置 outputLastMessageBytes 时，Clawsweeper 会从命令中移除 --output-last-message <path> 和 --json， 改为由 worker 从 Codex 的人读 stdout 中解析出最终消息（OutputLastMessageParser）， 再以 O_EXCL | 0600 独占写入受管路径。

为什么：Codex 进程不能决定文件最终落到哪里，也不能覆盖已有文件（wx）； 写入后会 fstat 校验“是普通文件且字节数完全一致”，失败时只删除自己创建的 inode。
src/codex-process-worker.ts:210–230
function writeManagedResult(path: string, text: string): void {
  const file = openSync(path, "wx", 0o600);   // 独占创建
  const owned = fstatSync(file);
  try {
    writeFileSync(file, text, "utf8");
    const metadata = fstatSync(file);
    if (!metadata.isFile() || metadata.size !== Buffer.byteLength(text)) {
      throw new Error("managed Codex result is not an exact regular file");
    }
  } catch (error) {
    // 只删除自己刚创建的 inode，避免误删他人文件
    const current = lstatSync(path);
    if (current.dev === owned.dev && current.ino === owned.ino) rmSync(path);
    throw error;
  } finally { closeSync(file); }
}

09二进制解析与 Windows 细节

“调用 codex”之前，先要确定 codex 到底是哪个文件。

src/codex-spawn.ts:21–59
export function codexProcessCommand(env, platform, cwd): string {
  const configured = env.CODEX_BIN?.trim();
  if (configured) return configured;            // 显式覆盖优先
  if (platform === "win32") {
    try {
      const pathInvocation = resolveSpawnCommand("codex", [], { cwd, env, platform, ... });
      if (windowsInvocationIsSpawnable(pathInvocation)) return "codex";
    } catch { /* 落到桌面版兜底 */ }
    const appBinary = windowsCodexAppBinary(env);
    if (appBinary) return appBinary;            // %LOCALAPPDATA%\OpenAI\Codex\bin\codex.exe
  }
  return "codex";
}

export function codexSpawnInvocation(args, env, platform, cwd) {
  const configuredCommand = codexProcessCommand(env, platform, cwd);
  return resolveSpawnCommand(configuredCommand, args, {
    cwd, env, platform,
    missingCommandMessage: `Unable to resolve Windows Codex command: ${configuredCommand}`,
  });
}

resolveSpawnCommand()（src/command.ts:280）在 Windows 上会：

  • 按 PATHEXT（.COM;.EXE;.BAT;.CMD）和 PATH 逐目录解析，并做大小写不敏感匹配。
  • 若命中 Node shebang 脚本，改用 process.execPath <script> 启动。
  • 若命中 .bat/.cmd，包一层 cmd.exe /d /s /c "…"，并启用 windowsVerbatimArguments。
