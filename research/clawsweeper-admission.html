什么样的 Issue 会进入 ClawSweeper？

以 openclaw/openclaw → openclaw/clawsweeper 为样本，拆解「issue 事件 → 队列准入 → 审查执行」的三层链路。结论先行：不是所有 issue 都会被审，但所有 issue 事件都会被投递。

Question · 是不是所有 issue 都给 ClawSweeper？

投递层：是 —— 每个 issue 事件都无差别转发进队列；
审查层：否 —— 是否真的跑一次审查，由仓库资格 + 队列准入 + 一次性完成去重 + 预算限流共同决定。

00先纠正一个前提

labeler.yml 不是「issue 关键字匹配」

.github/labeler.yml（525 行）每一条顶层键（"plugin: azure-speech"、"channel: discord"、"docs"、"cli"…）的值都是 changed-files → any-glob-to-any-file，即 actions/labeler 的「文件路径 glob」匹配，走 pull_request_target，作用于 PR 的改动文件。issue 没有 changed-files，这份配置对 issue 基本不生效。

真正给 issue 打「第一层」标签的是：ISSUE_TEMPLATE（bug_report → bug、feature_request → enhancement、docs_bug_report → bug + docs）与 auto-response.yml（Barnacle）。唯一的关键字匹配在 labeler 工作流的自定义步骤里，但那是 PR 标题 匹配 /\bbeta blocker\b/i → beta-blocker。

要点：目标仓打什么标签（plugin:* / bug / enhancement）不影响 ClawSweeper 准入 —— 标签选择与准入是解耦的。

01三层链路总览

注意三层的职责边界：目标仓只负责「转发事件」，所有资格判断、可见性校验、去重和写操作都发生在 ClawSweeper 的 Worker 与队列侧。

03三条调度路径（决定“何时”审，不决定“审不审”）

路径 触发 吞吐 / 节奏
exactexact event review 单个 issue / PR 的事件到达，即时审查这一条。 就是上文 dispatcher 投递进来的那条；受准入关卡与一次性完成去重约束。
hothot intake 新出现或近期活跃的队列边缘（target-fanout 游标扫描）。 每 20 分钟一轮，每轮 20 个目标仓（当前为临时限流节奏）。
backfillnormal backfill 到期需要回填的积压审查。 每 20 分钟一轮（14/34/54 分），每轮 12 个目标仓；手动回填上限 89 shard、下限 38 shard。

三条路径共享报告存储与 apply 规则，但刻意不共享吞吐——事件审查与热接入优先保证「新的、维护者可见的工作」快速得到响应，积压回填则让位于它们。

一句话总结：issue 事件无过滤投递，但「是否真的审」由仓库资格 + 队列准入 + 一次性完成去重 + 预算限流四道门共同决定；一旦进入，再由 intake 初筛与 full review 决定clawsweeper:* 建议标签。
