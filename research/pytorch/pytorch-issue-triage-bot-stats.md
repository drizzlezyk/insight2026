# PyTorch issue 分流：接入之后，谁在做什么

数据窗口：2025-11-01 ～ 2026-11-12  
数据量：`pytorch/pytorch` 全部 7,930 个 issue（GitHub Search API，按创建时间分片抓取）  
标签口径：2026-11-12 的**当前标签快照**（不是 issue 创建当时的标签）  
接入节点：2026-01-28 首次接入 Claude 版 issue-triage；2026-01-29 改为两段式；2026-10-29 换为 pi harness

---

## 0. 一句话结论

**机器人接管的是"分流"，不是"解决"。**

- 2026-01-30 之后共 5,949 个 issue，**79.9%** 被机器人打过 `bot-triaged`；剔除 CI 自动工单后 **89.6%**；普通社区 issue（general）**91.2%**。
- 但机器人真正独立关闭的极少：抽查 19 个"机器人判定可关闭"的样本，**15 个实际由 maintainer 或报告人关闭**，严格意义上的 bot 独立闭环只占 **10.5%–15.8%**。
- **完全接管（无需任何人类动作）≈ 0.5%–1.0%；分诊接管（分类/路由/关闭判断）≈ 77.3%。** 这是两个必须分开说的数字。
- 留给 maintainer 的是三段：**要决策的 299 个（12.7%）**、**已分类待修的 877 个 open（37.4%）**、**机器人没碰的 187 个（8.0%，其中 72% 其实已被人/其他工具打过标）**。
- 分诊质量在变好：人工打的 `bot-mislabeled` 从 2026-02 的 **7.9%** 降到 2026-08 的 **0.4%**，全程 140 个（占机器人动作 **3.1%**）。
- pi 版前 15 天：general 覆盖 **96.6%**，但转人工率 **27.9%**（Claude 期 11.1%）——模板预路由之后，机器人把更多硬 bug 升级给人，而不是自己下结论。

## 1. 机制：四条自动化通道 + 一个 agent

| 层 | 文件 | 触发 | 作用范围 | 机器人能做什么 |
|---|---|---|---|---|
| 1. probot labeler | `.github/pytorch-probot.yml` → `.github/labeler.yml` | PR 路径匹配 | **仅 PR** | 按文件路径打 `module:*` 等标签 |
| 2. label→label | `.github/pytorch-probot.yml` → `.github/label_to_label.yml` | PR + issue 标签事件 | PR + issue | 一个标签推另一个，如 `vllm-compile` → `module: vllm` + `oncall: pt2` |
| 3. test-infra autoLabelBot | `pytorch/test-infra` `torchci/lib/bot/autoLabelBot.ts` | issue 标题正则 | issue | `unstable`、`module: ci`、`skipped`、`module: rocm`、`module: vulkan` |
| 4. issue-triage agent | `.github/workflows/issue-triage.yml` + `issue-triage-pi.yml` | `issues: opened` → `workflow_run` | issue | 分类、打 `module:*` / `oncall:*`、升级 `triage review`、发模板评论、极少数关闭 |

agent 的关键边界（`scripts/issue_triage_pi/labels.py`、`apply_plan.py`）：

- 标签白名单来自 `.agents/skills/triaging-issues/labels.json`：**284 个**；运行时只过滤掉 `high priority`，即 **283 个可请求标签**。
- 代码层禁止：`^ciflow/`、`^test-config/`、`^release notes:`、`^ci-`、`^ci:`、`^sev`、`deprecated`，以及 `actionable`、`high priority`、`merge blocking`、`needs design`、`needs reproduction`、`needs research`、`oncall: releng`。
- **只加不删**；任何一次写操作都会补 `bot-triaged`；只有 pt2 / distributed 整条队列分诊完成时才补 `triaged`。
- 关闭只允许 `close_question`、`close_expected_behavior`（以及 duplicate / umbrella 策略），`state_reason=not_planned`。
- 因此 **`triaged` 不能当作机器人标记**：接入前的 1,929 个 issue 里已有 81.5% 带 `triaged`（无 oncall 的普通 issue 中是 88.5%），它来自人工或其他自动化；只有 `bot-triaged` 可靠。

两段式的意义：`plan` 作业只有只读工具 + Bedrock 模型，`apply` 作业有 `issues: write` 但没有模型。模型永远不能直接写仓库，写操作走确定性的 Python。

## 2. 总量：接入前 vs 接入后

| 时期 | issue 数 | `bot-triaged` | 覆盖率 | `triage review` | review 率 | 任一 `oncall:` | oncall 率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 接入前 2025-11-01..2026-01-27 | 1,929 | 49 | 2.5% | 45 | 2.3% | 830 | 43.0% |
| Claude 版 2026-01-30..2026-10-28 | 5,502 | 4,368 | 79.4% | 447 | 8.1% | 2,998 | 54.5% |
| pi 版 2026-10-29..2026-11-12 | 447 | 383 | 85.7% | 110 | 24.6% | 212 | 47.4% |

接入后合计 **5,949 个，机器人覆盖 4,751 个（79.9%）**。

其中 CI / 测试 / 文档批次类自动工单 1,379 个（23.2%），这类本来就有别的机器人管；把它们剔除后：

> **接入后非自动工单 4,570 个，机器人覆盖 4,096 个 = 89.6%。**

> 接入前那 49 个 `bot-triaged` 全部落在 distributed 队列，来自更早的分布式分诊自动化/回放，不影响接入后的口径。

## 3. 分队列：四条流水线，四种命运

接入后（2026-01-30 起）：

| cohort | 数量 | 占比 | 机器人覆盖 | 转人工 | 当前 open |
|---|---:|---:|---:|---:|---:|
| **general**（普通社区 issue） | 2,346 | 39.4% | 2,139 (**91.2%**) | 299 (12.7%) | 1,078 (46.0%) |
| **pt2**（`oncall: pt2`） | 1,829 | 30.7% | 1,583 (86.6%) | 129 (7.1%) | 786 (43.0%) |
| **distributed**（`oncall: distributed*`） | 395 | 6.6% | 374 (94.7%) | 76 (19.2%) | 210 (53.2%) |
| **automated**（CI/测试/文档批次） | 1,379 | 23.2% | 655 (47.5%) | 32 (2.3%) | 179 (13.0%) |

两条专用队列的真相是：**路由早就 100% 自动化了，只是执行者不同。**

- pt2：79.5% 由机器人打 `oncall: pt2` 路由，13.4% 是模板/其他工具在机器人运行前就带上了 oncall，机器人按 Step 0 直接跳过；7.1% 升级人工。
- distributed：75.4% 机器人路由，5.3% 预路由跳过，19.2% 升级人工。
- automated：30.9% 预路由跳过、21.6% 机器人完全没碰，所以覆盖率只有 47.5%——这不是机器人失败，而是这类工单本来就不该由它处理。

## 4. 互斥分类：机器人闭环 vs 人机协作 vs 留给人

general cohort，接入后 2,346 个：

| 结果 | 数量 | 占比 | 含义 |
|---|---:|---:|---|
| 机器人判定可关闭（近似） | 110 | **4.7%** | 机器人给了关闭理由/模板；抽查显示多数由人执行关闭 |
| 机器人路由到 oncall | 141 | **6.0%** | 转给 quantization / profiler / cpu inductor / jit 等 |
| 机器人打标、仍 open | 877 | **37.4%** | 分类完成，**等 maintainer 修** |
| 机器人打标、后被关闭 | 685 | **29.2%** | 分类完成，已解决 |
| 等待报告人补充 | 5 | 0.2% | |
| 转人工 `triage review` | 299 | **12.7%** | **需 maintainer 决策** |
| 已有 oncall，跳过 | 20 | 0.9% | |
| 机器人未处理 | 187 | **8.0%** | 其中 72% 已有人工/其他工具标签 |
| 其他关闭 | 22 | 0.9% | |

**"机器人做过动作" = 91.2%；"机器人只做分类、修复仍靠人" = 66.6%（1,562 个）；"机器人真正闭环" ≤ 4.7%，且实际关闭者多为人。**

### 4.1 对"自动关闭"桶的抽查校验

用 `/issues/{n}/timeline` 查关闭事件与评论的 actor，共 19 个样本（Claude 15 + pi 4）：

| 关闭者 | 样本数 | 占比 |
|---|---:|---:|
| 人类（malfet 10、janeyx99、soulitzer、OE-GOD、bahumanyarg11、li-lizhe） | 15 | **78.9%** |
| `github-actions[bot]` | 4 | 21.1% |
| 其中：机器人发过评论且无人类评论（严格 bot 闭环） | 2–3 | **10.5%–15.8%** |

典型链路是：机器人打 `module:*` 标签（有时发模板评论）→ maintainer 或报告人关闭。也有相当一部分是机器人只打了标、完全没评论，由人关闭（如 #174284，5 条人类评论、0 条机器人评论）。

反例同样存在：机器人误判为"预期行为"，人纠正后由报告人关闭（#202532）；机器人乱打标，maintainer 加 `bot-mislabeled` 后关闭（#176372）。

**结论：这个桶应理解为"机器人认为可以关闭 / 打标后被以 not_planned 关闭"，而不是"机器人关闭了"。机器人独立闭环的比例约为该桶的 10%–20%。**

### 4.2 三档"接管"口径

| 口径 | 定义 | 数量 | 占 general |
|---|---|---:|---:|
| **完全接管（严格）** | 机器人独立关闭，且无人类评论/关闭动作 | ~12–23（110 × 10.5%–21%） | **0.5%–1.0%** |
| **分诊接管** | 机器人完成分类/路由/关闭判断，无需人类决策 | 1,813（110+141+685+877） | **77.3%** |
| **需要人类决策** | `triage review` | 299 | 12.7% |
| **机器人未处理** | 无 `bot-triaged` | 187 | 8.0% |

"分诊接管"的 1,813 个里，人类仍然要做修复或最终关闭；机器人接管的是"这是什么、归谁、要不要关"的判断，不是"修好它"。

## 5. 留给 maintainer 的到底是什么

### 5.1 当前存量：1,078 个 open 的 general issue

| 内容类型（可多选） | 数量 | 占 open |
|---|---:|---:|
| bug / 正确性（crash、silent correctness、regression、NaN 等） | 382 | **35.4%** |
| feature / enhancement / function request | 251 | **23.3%** |
| performance | 91 | 8.4% |
| build / 安装 / 二进制 | 77 | 7.1% |
| docs | 64 | 5.9% |
| tests | 40 | 3.7% |
| security | 10 | 0.9% |
| 其他 / 无内容标签 | 336 | 31.2% |

其中 **91.9% 已经有 `module:*` 标签**，完全没有 module/oncall 标签的只有 15 个。也就是说：**maintainer 面对的是一条已经分好类、贴好签的待修队列，而不是一堆未分类的原始报告。**

### 5.2 需要决策的 299 个（`triage review`）

这 299 个不是"机器人失败"，而是机器人主动交给人判断的硬问题：

| 标签 | 数量 | 占 escalated |
|---|---:|---:|
| `module: correctness (silent)` | 93 | **31.1%** |
| `module: crash` | 57 | 19.1% |
| `module: mps` | 55 | 18.4% |
| `module: cuda` | 54 | 18.1% |
| `module: regression` | 54 | 18.1% |
| `module: linear algebra` | 30 | 10.0% |
| `high priority` | 27 | 9.0% |

pi 版窗口里升级的 issue 标题几乎是清一色的静默正确性问题：`scatter_add` 写错行、`conv2d` 返回未初始化内存、`layer_norm` jvp 返回 NaN、`ctc_loss` 反向传播 inf……**这正是最需要人判断、也最不该让 bot 自动关掉的一类。**

这类 issue 处理得很快：

| 指标 | Claude 版 escalated（n=235） |
|---|---:|
| 已关闭 | 234（99.5%） |
| 关闭耗时中位 | **0.9 天** |
| p75 | 2.0 天 |
| p90 | 5.1 天 |

pi 窗口当前仍有 50 个 open 的 escalated，中位挂起时间 1.8 天、p90 6.8 天——是一条**周转很快的人工决策队列**，不是积压。

### 5.3 机器人没碰的 187 个

| 子类 | 数量 | 占未处理 |
|---|---:|---:|
| 已有人工/其他工具标签（`triaged`、module、oncall） | 135 | 72.2% |
| 完全空白（无 module/oncall/triaged） | 52 | 27.8% |

"机器人未处理" ≠ "没人处理"。真正完全空白的只有 52 个，占 general 的 2.2%。

### 5.4 关闭吞吐：机器人没有让 issue 关得更快

| 指标 | 接入前 general | Claude 版 general |
|---|---:|---:|
| 30 天内关闭率 | 47.3% | 45.8% |
| 已关闭 issue 的中位关闭天数 | 6.0 | 4.7 |
| 有 module 标签 | 81.0% | 88.7% |
| 无 module / oncall | 14.8% | 6.2% |

**分诊质量显著提升（无标签率 14.8% → 6.2%），但关闭吞吐基本持平。** 机器人压缩的是"从创建到被正确分类"的时间，不是"从创建到被修复"的时间。

分路径看 Claude 版的关闭耗时：

| 路径 | 中位关闭天数 | p75 |
|---|---:|---:|
| 判定可关闭 | 0.7 | 5.5 |
| 转人工 review | 0.9 | 2.0 |
| 未处理 | 3.1 | 14.1 |
| 打标后关闭 | 10.8 | 31.0 |
| 路由 oncall | 16.4 | 62.8 |

### 5.5 负担有没有变轻：按 100 个 general issue 记账

接入后每 100 个 ordinary issue 的人类参与情况：

| 结果 | 每 100 个 | 人类是否必须介入 |
|---|---:|---|
| 机器人独立闭环 | **~1** | 否 |
| 机器人判定可关闭、人执行 | ~4 | 是（仅关闭动作） |
| 机器人路由 oncall | 6 | 是（由 oncall 修） |
| 机器人打标后已解决 | 29 | 是（修复/关闭） |
| 机器人打标后仍 open | 37 | 是（修复） |
| 转人工 review | 13 | 是（决策） |
| 未处理 | 8 | 是（其中 6 个已有人工标签） |
| 其他 | 1 | — |

三条互相印证的结论：

1. **分类负担确实下降**：无 module/oncall 标签的比例 14.8% → 6.2%（Claude）→ 3.4%（pi）；有 module 标签 81.0% → 88.7% → 90.1%。
2. **修复负担没有下降**：30 天内关闭率 47.3% → 45.8%，基本持平；open 存量 1,078 个，且 91.9% 已分类。
3. **决策负担反而显式化**：`triage review` 从接入前的 2.8%（19/670）升到 11.5%（242/2,113）。这不一定是新增工作量——更可能是把过去"没人明确表态"的疑难 issue 变成了显式决策请求——但它确实意味着 maintainer 要做的判断变多了，而不是变少了。

**净效应：负担从"读 issue、猜归属、贴标签"转成了"做判断、修 bug"。总量没有明显减少，但单位时间的有效产出更高，队列更干净。**

## 6. 质量反馈：`bot-mislabeled`

maintainer 用 `bot-mislabeled` 显式标记机器人打错标。这是目前唯一可直接观测的 precision 信号（是下限，不是全量误差）。

| 时期 | `bot-mislabeled` | 占 `bot-triaged` |
|---|---:|---:|
| Claude 版 | 134 | **3.1%** |
| pi 版 | 6 | **1.6%** |

按 cohort：general 98、pt2 35、distributed 5、automated 2。

月度趋势（占当月机器人动作）：

| 2026-02 | 03 | 04 | 05 | 06 | 07 | 08 | 09 | 10 | 11 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 7.9% | 10.4% | 3.6% | 4.6% | 0.8% | 0.9% | 0.4% | 0.2% | 1.2% | 1.0% |

2–3 月是规则磨合期，6 月之后稳定在 1% 上下。**这是 skill/提示词迭代起作用的直接证据。**

## 7. Claude 版 vs pi 版（2026-10-29 起）

general cohort：

| 结果 | Claude（9 个月） | pi（15 天） |
|---|---:|---:|
| 机器人覆盖 | 90.6% | **96.6%** |
| 判定可关闭 | 5.1% | 1.3% |
| 路由 oncall | 5.9% | 7.3% |
| 打标、仍 open | 36.0% | **50.2%** |
| 打标、后关闭 | 31.3% | 10.3%（时间未到） |
| 转人工 review | 11.1% | **27.9%** |
| 未处理 | 8.6% | 2.6% |

三个真实的行为差异：

1. **更严格执行"已有 oncall 就跳过"**：pt2 覆盖率 87.7% → 69.2%，跳过率 12.3% → 30.8%。不是能力下降，而是不再重复路由。
2. **升级率翻倍以上**：general 11.1% → 27.9%，distributed 16.2% → 56.7%。新 harness 对不确定的硬 bug 更倾向交给人，而不是自己判"预期行为"。
3. **误标率减半**：3.1% → 1.6%。

代价是：`labeled_open` 占比从 36.0% 升到 50.2%，即**更多 issue 以"已分类、待修"的状态停在 maintainer 队列里**。这不是 pi 变差，而是它更少做"关闭"这个高风险动作。

15 天窗口太短，关闭类指标（判定可关闭、打标后关闭）不可与 Claude 期直接比较；覆盖、路由、升级、误标这四类即时指标可比。

## 8. 对洞察报告的启示

1. **AI 在开源维护中的真实位置是"分诊层"，不是"解决层"。** 它把 90% 的 issue 变成了带标签、带队列、带优先级的结构化工作项，但修复仍然由人完成。用"机器人关闭了多少 issue"衡量会严重低估它的价值，也会误判它的风险。
2. **maintainer 的剩余工作被压缩成两种：决策与修复。** 决策量约 13%，且周转极快（中位 0.9 天）；修复量是 37% 的 open 存量，且已经分好类。真正"没人管"的空白 issue 只有 2.2%。
3. **机器人越保守，人越忙但越安全。** pi 版把升级率提到 27.9%，同时把误标率压到 1.6%，代价是待修队列变长。这是一个明确的产品取舍，而不是能力退化。
4. **模板预路由会挤压 agent 的路由价值。** 当 pt2/distributed 模板自带 `oncall:` 标签，agent 的覆盖率和路由量都会下降，它的价值转向"分类 + 升级 + 写模板回复"。评估 agent 时必须把模板预路由剔除，否则会得出"机器人变差了"的错误结论。
5. **质量闭环比准确率更重要。** `bot-mislabeled` 这种人工反馈标签，让误标率从 10% 降到 0.4% 变得可观测、可迭代。没有这个反馈通道，agent 的准确率无法治理。
6. **关闭动作要单独治理。** 关闭是唯一不可逆的写操作，当前实际关闭率极低（抽查 1/9），说明护栏生效；但也意味着"自动关闭"在统计上几乎不构成机器人的主要贡献，不应作为核心 KPI。

## 9. 方法与局限

- **数据源**：GitHub Search API `repo:pytorch/pytorch is:issue created:<range>`，按日期分片、按 `created` 升序翻页，去重后 7,930 条。无 token，全部匿名请求（search 10 次/分，core 60 次/时）。
- **标签是当前快照**：一个 2025-12 创建的 issue 可能在 2026-02 才被打上 `bot-triaged`，因此"接入前"时期的覆盖率不是 0（distributed 有 49 个）。
- **`triage review` 标签不会在关闭时移除**，所以 escalated 桶包含历史已处理项；这也是它关闭率高达 82.9% 的原因。
- **pi 窗口只有 15 天**，关闭类指标右删失严重。
- **关闭 actor 抽查 19 个样本**（core API 配额限制），用于定性校验与区间估计；"0.5%–1.0%"是按该样本比例外推的近似值，不是全量精确值。
- **cohort 定义**：
