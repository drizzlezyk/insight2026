SNAPSHOT 2026-11-06 · READ-ONLY
OpenClaw × ClawSweeper · 社区维护者提效拆解

Dashboard 不替维护者做决定，
它让决定变得可定位。

ClawSweeper 的只读观察台，把六万多条 issue 的噪音压缩成一组可讨论的队列：系统是否健康、哪里堵住、哪些条目需要人。它的提效不在“关掉多少”，而在少找多久、少看多少、先看哪一条。

有帮助

它降低的是“系统状态的搜索成本”：把队列、覆盖、审查结果和运行健康收进一个只读面，让维护者先判断“值不值得去 GitHub 看”。

还不够

它还不是一张“今天该我处理什么”的清单。多数页面为运维者设计，公共分诊只有聚合计数，评估是保存记录，不保证当前仍有效。

有方向

从“系统观察台”升级为“维护者决策台”：按人、按优先级、按证据新鲜度组织下一步，而不是再加一块指标。

The Loop

提效发生在一条五步链上，Dashboard 只占第一步。

ClawSweeper 把维护者的工作拆成“看系统 → 找条目 → 做判断 → 发命令 → 受控执行”。Dashboard 负责第一步；真正处理仍在 GitHub。它的产出不是动作，而是下一步的入口。

  1. 01Observe

    发现信号

    看队列、吞吐、覆盖与审查评估；判断系统是否在工作、哪里有异常。

  2. 02Locate

    定位条目

    从聚合样例跳回 GitHub Issue/PR；读证据、标签、报告与决策包。

  3. 03Decide

    完成判断

    补信息、验证复现、决定产品行为，或安排安全与维护者复核。

  4. 04Request

    发出请求

    @clawsweeper review / re-review / explain / stop；命令经权限与当前评论校验。

  5. 05Apply

    受控执行

    标签同步或满足条件的关闭由独立 Apply 车道完成；不是在 Dashboard 点按钮。

看见 ≠ 操作。 Dashboard 是只读观察台，不是 GitHub 管理后台。发现问题的页面和解决问题的页面，刻意分开。

Outcome

社区结果在变好，但别把相关性当因果。

全社区 issue cohort 在接入前后出现了很大的闭合率差异。这个数字值得看，但它不是 ClawSweeper 的净因果提升——同期的流量、issue 构成和其他自动化都在变化。

Limits

Dashboard 的五个“不”。

这些不是缺陷清单，而是使用说明。它们决定了正确的读法：把 Dashboard 当作“去哪里查”的索引，而不是“结论是什么”的判决书。

01
不是实时

站点构建约每 15 分钟；队列与运行遥测可更频繁；审查总量、评估和关闭汇总约每日两次更新。

先看页首的 Snapshot、Reviews、Queue 时间，再判断数据是否足够新。

02
不是完整清单

未认证 observer API 只返回固定聚合字段和 allowlist 范围的公开引用；页面样例有上限，不构成完整清单。

排查具体事件要回 GitHub / 授权运维渠道，不要拿页面样例当全量。

03
不是当前事实

Assessments 和 Repositories 主要基于已保存报告；历史状态不能证明条目现在仍 open、来源仍匹配或问题已经解决。

“Unknown”不要读成“没有问题”；到 GitHub 核对 live 状态与最新报告。

04
不是准确率报告

评估是审查者判断，不是验证过的严重度；未见公开 gold-set、precision / recall。护栏能拦截格式错误与越权写入，不能保证语义判断正确。

把评估当“值得抽查的线索”，不要当“已验证的结论”。

05
不是通用服务

官方实例服务 OpenClaw / steipete 生态；其它社区接入需自行托管，并配置目标仓 dispatcher、App、Worker 与权限。

Dashboard 页面可以作为设计参考，不代表第三方仓能直接加入官方实例。

Playbook

其它社区可以照搬的 7 条设计原则。

ClawSweeper 的 Dashboard 不是“漂亮图表”的集合，而是一套观察纪律。下面这些原则，比具体的页面布局更值得复制。

01

按问题组织页面，不按数据表组织。

每个页面先写清楚“它回答哪个维护问题”，再决定放哪些指标。问题先行，指标随后。

02

观察与执行分离。

Dashboard 永不写 GitHub；所有写操作回到 GitHub 或受控 Apply 车道。看见和操作之间，留一道权限与实时校验。

03

每个数字带口径、时间戳和 Unknown。

快照时间、样本窗口、分母、是否可重叠。不知道就写 Unknown，不用旧数据伪装实时。

04

角色分层。

维护者、运维者、公众看到不同的投影；公开页只给聚合，不给逐条隐私。

05

结论必须能回到证据。

每个标签、评估、样例都能跳回 GitHub 条目；Dashboard 不是 source of truth。

06

把“下一步”做成显式路径。

Observe → Locate → Decide → Request → Apply；不要让维护者在图表里自己找入口。

07

把失败和缺口放在首页。

队列积压、backoff、handoff、覆盖缺口、stale 样例。系统先分诊自己的失败，再让人看到。

Direction

下一步不是更多指标，
而是一张“今天该我判断”的清单。

ClawSweeper 已经把“观察”和“分诊”做得很完整。社区可以补上的，是两者之间的一层：把系统信号翻译成某个维护者今天能执行的下一步。

What to do next

维护者决策台应该回答五个问题

  1. 本周哪些条目只有我能决定？
  2. 哪些结论已经过期，或证据不足？
  3. 哪些关闭 / 标签值得抽样复核？
  4. 哪些重复劳动可以被挡住？
  5. 这周我们的判断错在哪里？

指标要能回答“维护者省下了什么”，而不只是“系统跑了多少”。

指标它回答什么不要用它做什么
首次有意义响应时间贡献者是否被看见不要用总评论量替代
人工关闭的证据覆盖率判断是否有据不要当自动化率
误关复活率执行质量不要追求零；会牺牲召回
维护者负载集中度社区是否可持续不要只看 top-5
队列最老等待时间系统是否健康不要当社区健康
01

只读接入

2–4 周

事件转发、耐久报告、单条评论；不开任何关闭。先验证“看得见”。

02

建议性分诊

4–8 周

只写 advisory labels；抽样复核 precision；不建 PR、不合并、不关闭。

03

受控执行

按仓库开启

逐条开启 close rules；保留复活、审计与人工否决。先观察，再放开关闭。

Field Note / 2026-11-15

一个好的社区仪表盘，最终要让维护者更容易说：“这条不用我看。”

先让系统可见，再让判断可定位，最后才让动作可执行。顺序反了，仪表盘就会变成另一份需要维护的 backlog。

Method
