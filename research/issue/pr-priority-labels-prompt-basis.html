PR 的 P0–P3 标签：没有专属 rubric，
只有共享的一行

PR 侧并没有自己的 triagePriority 评分表。唯一直接规定 item 优先级的是 issue 与 PR 共享的 prompts/review-item.md:51；PR 专属 prompt 里出现的 P0–P3 全部是 reviewFindings[].priority（单条 finding 的等级），不是 GitHub 上的 P0/P1/P2/P3 标签。schema 只给五档一句话定义，代码只做 triagePriority → 同名标签的确定性映射。

上游核验 openclaw/clawsweeper@c0b05e4 核验日期 2026-11-16 对照 prompts/ · schema/ · src/
一句话结论

PR 的 P 标签不来自 finding 等级，也不来自 workPriority；它只来自顶层字段 triagePriority，而这个字段的判定标准只有共享 prompt 的一行字。

00 · 先分清三个“P0–P3”

同一个仓库里有三套看起来都像“优先级”的东西，但只有第一套会变成 GitHub 标签。把三者混在一起，是读 PR prompt 时最常见的误判来源。

关系 01

P 标签只有一个来源

priorityLabelForTriage 只读 TriagePriority；syncPriorityLabel 也只接收 triagePriority。它从不读取 reviewFindings。

关系 02

finding 等级管“必不必做”

P0–P2 是 required work，P3 是 advice 且 never blocks merge；patch is incorrect 只在列出的 P0–P2 finding 阻止 merge 时成立。

关系 03

两者被要求“分开判断”

prompt 明确要求 item 优先级与 finding 优先级分开；但也没有规定两者必须一致，代码不做一致性校验。

workPriority 与 P 标签无关。prompt 里没有以字段名出现；schema 只给枚举、没有描述；parser 只做 high/medium/low 校验。它不在任何标签映射或 apply 路径中。

共享行 review-item.md:51 的完整结构是一条带前置覆盖规则的判定链，而不是一张打分表。原文如下（节选完整句子）：

prompts/review-item.md:51 · Labels, UX override first
Labels, UX override first: a non-technical first-time or community user blocked in website/download/install/update/setup/onboarding/auth/provider setup/first useful run/in-product recovery with no in-product way forward (recovery needs terminal commands, config or file edits, log inspection, internal knowledge, or maintainer/support help) is P0 plus impact:ux-release-blocker … Recoverable docs/support/guessing paths are P1/P2 plus impact:ux-friction; cosmetic or fully recoverable in-product confusion is P2/P3; advanced or power-user terminal/config workflows are not promoted. UX override 的四种情形

情形结果原文要点
非技术背景的首次/社区用户，在 website/download/install/update/setup/onboarding/auth/provider setup/first useful run/in-product recovery 被卡住，且产品内无路可走 P0 + impact:ux-release-blocker 恢复需要 terminal、改配置/文件、看日志、内部知识或维护者支持；同时要求 bestSolution/workReason 推荐 Doctor/Fix button、setup wizard、inline recovery 或 visible command launcher。
可恢复的 docs / support / guessing 路径 P1/P2 + impact:ux-friction “Recoverable docs/support/guessing paths”
纯 cosmetic，或完全可在产品内恢复的 confusion P2/P3 “cosmetic or fully recoverable in-product confusion”
advanced / power-user 的 terminal、config 工作流 不升级 “advanced or power-user terminal/config workflows are not promoted”

对 PR 来说，UX override 只能落地一半。它要求同时挂 impact:ux-release-blocker/impact:ux-friction，但 schema 标注 impact 为 Issue-only，代码在 PR 上把 impact 置空。因此 PR 只得到 P 部分，impact 部分被丢弃——这是 prompt 与代码之间最明显的错位。

03 · 等级依据表 schema 定义 vs PR finding 例子

PR prompt 里确实有 P1/P2/P3 的 finding 场景，但那是 finding 等级的例子，不是 item 标签的例子。P0 甚至没有任何 PR 侧的具体例子，只能回到 schema 的“Emergency”定义。

等级schema 定义PR prompt 中的具体例子（finding 语境）硬边界
P0 Emergency: data loss, security bypass, crash loop, or unusable core runtime. 没有给出任何具体 PR 例子。PR prompt 只写 “P0-P2 rank impact”；schema 对 finding 0 只写 “0=P0 critical”。 required work；列出的 P0 finding 可使 overallCorrectness: "patch is incorrect"。
P1 Urgent regression or broken agent/channel workflow affecting real users now. 重新实现配置/docs/CLI flags/env vars/现有 API/plugins/skills/setup 已有的能力；upgrade 会 break setups、覆盖 config/preferences、静默替换行为、产生竞争性 source of truth；plugin API 的机械修复。 required work；plugin API 机械修复可 queue_fix_pr。
P2 Normal priority bug or improvement with limited blast radius. 新增 AGENTS.md/skill/prompt 规则但未引用 incident；smallest complete fix 中不必要的 production machinery；为 speculative/极不可能 race 或 security edge case 增加 machinery（且无具体 failure mode）；upgrade 行为本身保持但缺 migration/docs/upgrade proof。 required work。
P3 Low-risk cleanup, docs, polish, ergonomics, or speculative feature. 非 production 的 test scaffolding/多余结构；只有一个 caller、提前抽出的 helper；low-risk discoverability 或 docs gap。 advice，never blocks merge or changes the verdict；但窄小的机械 blocker 仍可为 queue_fix_pr，“even when process-only or P3”。
none no priority label. 无。 代码移除所有 P 标签且不添加；prompt 未规定何时该用 none 而不是 P3。

补充：finding 的 P3 是 “a real low-impact defect”，不是“随便的建议”；P0–P2 “rank impact”，P3 只是不阻塞 merge。把 finding 例子直接当作 item 标签判据，会高估 P 标签的严格程度。

04 · 与 finding priority 的关系 独立选择，不自动继承

finding 侧

P0–P2 必做，P3 建议

“A finding is required work at P0-P2 and advice at P3, which never blocks merge or changes the verdict.” finding 还必须有 actual introduced trigger、causal link、failing input and wrong result。

item 侧

四维独立判断

prompt 的措辞是 “separately from finding priorities and repairability”。schema 把 triagePriority 与 reviewFindings 放在两个独立字段；代码只映射前者，parser 也不比较两者。

实践含义：一个 PR 可以含 P0/P1 finding，但 item 仍被标为 P2/P3，只要该 PR 整体对用户的影响/紧迫性不高；反过来，一个紧急用户问题对应的 PR 即使只有 P2 级实现瑕疵，也可以获得较高的 item 优先级。prompt 没有“取 finding 最大值”或“不得低于最高 finding”的规则。

未解决的语义边界：对 PR，triagePriority 衡量的是“这个改动要解决的问题有多重要”，还是“这个 PR 自身引入的缺陷有多严重”？schema 描述偏 issue 语境（“bug or improvement”），prompt 只说 “for the whole item”，代码直接透传，没有澄清。

05 · 不能仅凭这些因素升 P

下表把“明确针对优先级标签的规则”与“相邻但并非针对优先级的规则”分开。只有 CI 一行是 prompt 对 triagePriority 的显式限制；其余多为 finding、work lane 或 rating 规则，不能当作 P 的正向判据。

06 · 代码强制层 一标签一理由，精确匹配

强制 01

labelJustifications 集合相等

每个对象含 label + reason；parser 要求数组、拒绝重复 label，并分别检查 missing selected labels 与 unselected labels，任一不匹配直接抛错。

schema:460-500 · parser:305-355,1033

强制 02

枚举只接受五档

requireEnum(..., TRIAGE_PRIORITIES, ...) 只接受 P0/P1/P2/P3/none；映射表硬编码 0→P0、1→P1、2→P2、3→P3，没有模糊匹配。

parser:912-916 · policy:602

强制 03

none 会清掉旧标签

nextPriorityLabels 先过滤全部 PRIORITY_LABEL_NAMES，再按映射追加；none 返回 null，所以结果是“没有 P 标签”，而不是保留旧值。

label-selection:72-83 · test/pr-label-policy:668-672

强制 04

PR 抑制 impact/maturity，但 P 仍生效

nextPriorityLabels 无条件应用；nextImpactLabels/nextMaturityLabels 在 PR 时收到 []。apply 路径同样如此。

label-presentation:106-110 · apply-report-labels:173-199

范围细节：精确匹配只覆盖 triagePriority、impactLabels、mergeRiskLabels、maturityLabels 四类 review label。PR 的 rating:、status:、proof: 等标签的 justification 由 presentation 层另行生成，不要求模型在 labelJustifications 里逐条列出。

测试固定的 justification 示例
triage_priority: "P1" → {"label":"P1","reason":"The PR changes an active channel workflow affecting real users."}
渲染结果为 “Label justifications:” 下的 - `P1`: …。理由直接引用 P1 定义中的 “active … workflow affecting real users”，而不是复述 finding。

07 · 边界与容易误读的地方

01

PR 没有专属 rubric

唯一指令是共享的 review-item.md:51；PR-only prompt 里的 P0–P3 全是 finding 等级。不要把它当成 PR 标签清单。

02

P0 finding 例子缺失

PR prompt 给出了 P1/P2/P3 finding 的具体场景，但没有任何 P0 finding 的具体 PR 例子；P0 只能依赖 schema 的 “Emergency” 与 “0=P0 critical”。

03

none 没有细化标准

schema 只说 “no priority label”；prompt 没有说明何时该用 none 而非 P3。可确定的只有代码行为：移除全部 P 标签。

04

UX override 与 PR 不兼容

它要求同时挂 impact 标签，但 impact 是 Issue-only，代码在 PR 上置空。对 PR 应整体跳过还是只取 P 部分，prompt 未规定；代码只能执行后者。

05

共享行可能是唯一指令

review-item.md:51 同时承担 UX override、四维、CI 例外和理由要求；没有第二处解释或决策树。若该行被修改，PR 与 issue 的 P 标签行为会一起改变。

06

语义对象未定义

对 PR，它是“改动要解决的问题有多重要”，还是“PR 引入的问题有多严重”？schema 偏 issue 语境，prompt 只说 “for the whole item”，代码直接透传。

07

workPriority 不是隐藏来源

prompt 未以字段名提及，schema 无描述；不要把它当作 P 标签的第二个来源。

08

精确匹配 ≠ 语义正确

parser 只保证“选中的 label 与 justification 集合完全一致”，不保证理由质量，也不保证 triagePriority 与 finding 等级/PR 评级自洽。

结论

1 · 一个字段

P 标签只来自 triagePriority；finding 等级与 workPriority 都不会变成 P 标签。

2 · 一行判据

PR 没有专属评分表，只有共享的 review-item.md:51：UX override 优先，否则按整条 item 的四维判断。

3 · 一层错位

UX override 要求的 impact 标签在 PR 上被代码置空；PR 只落地 P 部分，prompt 未规定这种情形怎么处理。
