01 · 五档定义 schema 是唯一出处

等级定义只写在 schema 里，prompt 不复述。schema 用一个字符串把五档一次说清；代码里的标签描述与它逐字一致。

schema/clawsweeper-decision.schema.json:363-366 · triagePriority
P0: Emergency: data loss, security bypass, crash loop, or unusable core runtime. P1: Urgent regression or broken agent/channel workflow affecting real users now. P2: Normal priority bug or improvement with limited blast radius. P3: Low-risk cleanup, docs, polish, ergonomics, or speculative feature. none: no priority label.
标签schema 定义维护者怎么读
P0Emergency: data loss, security bypass, crash loop, or unusable core runtime.会丢数据、绕过安全、崩溃循环，或核心运行时不可用——先止血，不代表好修。
P1Urgent regression or broken agent/channel workflow affecting real users now.现网用户正在受影响的回归或 agent/channel 工作流中断——需要尽快安排。
P2Normal priority bug or improvement with limited blast radius.普通 bug 或改进，影响面有限——常规队列。
P3Low-risk cleanup, docs, polish, ergonomics, or speculative feature.低风险清理、文档、打磨、易用性，或投机性功能——有空再做。
noneno priority label.不挂 P 标签；prompt 没有给出何时该用 none 的细化标准。

注意作用域：triagePriority 没有标注 “Issue-only”（对比 impact 的 “Issue-only, at most 3” 与 maturity 的 “Issue-only”），所以它是 issue 与 PR 共用的 item 级字段。本文只讨论 issue 侧。

02 · 判定链 覆盖规则优先，然后四维，最后写理由

完整判据就是共享行的这一句。它是一条带前置覆盖规则的判断链，不是打分表，也没有“影响 +1、崩溃 +2”之类的加权。

prompts/review-item.md:51 · Labels, UX override first
Labels, UX override first: a non-technical first-time or community user blocked in website/download/install/update/setup/onboarding/auth/provider setup/first useful run/in-product recovery with no in-product way forward (recovery needs terminal commands, config or file edits, log inspection, internal knowledge, or maintainer/support help) is P0 plus impact:ux-release-blocker … Recoverable docs/support/guessing paths are P1/P2 plus impact:ux-friction; cosmetic or fully recoverable in-product confusion is P2/P3; advanced or power-user terminal/config workflows are not promoted. Otherwise choose triagePriority from user impact, severity, confidence, and urgency for the whole item, separately from finding priorities and repairability; failing, pending, or flaky CI raises it only for user-facing automation failures or diff-caused urgent regressions. … justify each selected label once.
01

UX override：先问“非技术用户是不是被卡死”

是，且产品内无路可走 → P0 + impact:ux-release-blocker。可恢复的 docs/support/guessing 路径 → P1/P2 + impact:ux-friction；纯 cosmetic 或产品内可恢复 → P2/P3；高级用户的 terminal/config 流程明确不升级。

user impact、severity、confidence、urgency。是 “for the whole item”，不是只看标题、只看某一条评论，也不是只看一个 impact 标签。

03 · UX override issue 侧唯一会“强制”改 P 的规则

这条规则的特殊之处在于：它先于通用四维，并且直接把 P 值与 impact 标签绑定。对 issue 来说，两半都能落地——这正是它与 PR 的关键差异。

情形结果原文条件 / 要点
非技术背景的首次/社区用户，在 website/download/install/update/setup/onboarding/auth/provider setup/first useful run/in-product recovery 被卡住，且产品内无路可走 P0 + impact:ux-release-blocker “no in-product way forward”：恢复需要 terminal commands、config/file edits、log inspection、internal knowledge，或 maintainer/support help。还要求 bestSolution/workReason 推荐 Doctor/Fix button、setup wizard、inline recovery 或 visible command launcher。
可恢复的 docs / support / guessing 路径 P1/P2 + impact:ux-friction “Recoverable docs/support/guessing paths”
纯 cosmetic，或完全可在产品内恢复的 confusion P2/P3 “cosmetic or fully recoverable in-product confusion”
advanced / power-user 的 terminal、config 工作流 不升级 “advanced or power-user terminal/config workflows are not promoted”——不能因为“用户被卡住”就自动 P0，先看用户画像与恢复路径。

两个细节：同一证据同时支持 ux-release-blocker 与 ux-friction 时优先前者；能选具体标签时不要选 impact:other。另外，“claim no more certainty than the evidence” 同样约束 P——不要把推测写成紧急。

它不是“严重度”规则，而是“可恢复性”规则。一个安装引导问题可能没有任何崩溃，却因为非技术用户在产品内无路可走而判 P0；反过来，一个高级用户的 terminal 报错即使很烦，也不会被这条规则自动升级。

04 · 通用四维 没有命中 override 时看什么

维度 01

user impact

影响的是谁、多少用户、是否阻断真实使用。不是“代码看起来多严重”。

维度 02

severity

问题本身的损害程度：数据、安全、崩溃、工作流中断，还是体验摩擦。

维度 03

confidence

证据有多硬：能否复现、证据是当前 main 还是源码推断、报告是否完整。证据不足不能升 P。

维度 04

urgency

现在就要处理，还是可以排队。现网回归、发布阻断比“以后会坏”更急。

“separately from finding priorities and repairability” 对 issue 的含义：issue 的 reviewFindings 恒为 []，所以“finding 优先级”这一半是空的；但“repairability”仍然有效——不要因为“看起来好修”就升 P，也不要因为“很难修”就降 P。P 值判断的是影响与紧迫性，不是工作量。

P 值是聚合判断，不是从单一维度查表。impact 标签回答“坏在哪”，复现状态回答“证据有多硬”，路由标签回答“下一步谁来做”；它们都可能成为判断输入，但没有任何代码把其中某一个字段自动换算成 P。最终的 P 仍是模型对整条 item 的四维判断。

窗口 2026-09-13..11-13，GitHub 搜索 API 快照。P 标签是单选项，四数之和为窗口内带 P 标签的 issue 数。completed = 已解决/有修复落地；not_planned = 未解决（无法复现、不修、重复等）。

一眼结论：P 值呈“中间大两头小”的钟形，P2 占 56%。但 completed 占比并不随优先级单调下降——P1 最高（79.6%），P0 只有 58.0%。原因是 P0 里有大量“用户以为是紧急事故、实则是误报或不可行”的情况，被快速以 not_planned 关掉；P3 作为低优先级 cleanup/feature，近一半最终被搁置。这也印证：P 标签给的是处理顺序和预期节奏，不是“一定会修”的承诺。

08 · 边界与容易误读的地方

01

P0 ≠ 好修

P0 只是“紧急/损害大”。数据丢失、安全绕过往往需要更谨慎的修复与验证；紧急不等于简单。

02

P 值不从 impact 自动推导

impact 回答“坏在哪”，P 回答“多紧急”。同一 impact 可以对应不同 P；代码也没有这条换算。

03

评级不是严重度

issue-rating: 评的是报告可验证度/证据强度，与 P0–P3 正交。高评级不等于高优先级。

04

workPriority 不是来源

它不进入任何标签映射；prompt 没有以字段名给出判据，schema 也没有描述。

05

none 没有细化标准

schema 只说 “no priority label”；prompt 没有说明何时该用 none 而非 P3。可确定的只有代码行为：移除全部 P 标签。

06

UX override 是唯一硬覆盖

它先于四维，且明确“power-user terminal/config workflows are not promoted”。不要把“用户被卡住”当成无条件 P0。

07

CI 例外不是 issue 判据

共享行里的 CI 规则针对 required check；issue 场景通常没有承载对象。不要用“CI 红了”给 issue 升 P。

08

理由集合精确匹配 ≠ 理由正确

parser 只保证每个选中标签恰好一条 justification，不保证理由质量，也不校验 P 与 impact/复现/路由是否自洽。

结论

1 · 先覆盖

UX override 先于一切：非技术用户 + 产品内无路可走 → P0；高级用户 terminal/config 流程明确不升级。

2 · 再四维

没有命中 override 时，按整条 item 的 user impact、severity、confidence、urgency 选一个 P 值。

3 · 后翻译

代码只做 triagePriority → 同名标签的一比一映射；优先级是排序，不是严重度评分，也不是修复承诺。
