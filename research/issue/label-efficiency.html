标签体系到底怎么帮维护者提效：不是完成率，是时间与注意力

你说得对——光看 completed 占比，很多维度确实拉不开差距。但「完成率」从一开始就量错了东西：not_planned 常常是正确的过滤（机器人把烂 issue 挡掉，维护者零耗时），completed 也未必是维护者干的活（可能是作者自己的 PR）。真正的效率藏在两条轴上：一件事多久被了结（时间），以及了结它的是人还是机器人（注意力）。下面就用窗口内真实 issue 逐条看。

这就是提效的第二层：看 needs-product-decision——它的 completed 占比只有 36.4%（表 01 里最低），但这不是「失败」，而是机器人替维护者扛下了 53% 的收尾：issue 挂着等决策，等不到就由 barnacle 自动关掉，维护者全程只碰了三分之一。反过来 queueable-fix 的 98.5% completed 也不是「机器人的功劳」，而是机器人把「修法已经清晰」的活筛出来，让维护者花最短时间真修掉。标签体系做的不是「提高完成率」，而是把每个 issue 路由到最便宜的那个关闭者。

04 · 合起来：两条车道 一条 0.5 天，一条 30 天

把「时间」和「谁在干活」叠在一起，标签体系在窗口内真实地造出了两条车道。

快车道 · 现在就能修

queueable-fix · fix-shape-clear · linked-pr-open · no-stale

中位 0.5–1.6 天
  • 机器人已确认「修法清晰 / PR 已开」
  • 维护者 / 他人关闭占 65–84%——真人真修
  • completed 占比 86–99%——筛出来的基本都修掉了
  • 本质：机器人先把诊断做完，人只写修复

慢车道 · 先挂着等

needs-product-decision · needs-maintainer-review · stale

中位 26–44 天
  • 机器人判定「卡在决策 / 要细审 / 已过期」
  • barnacle 关闭占 33–75%——机器人在等、在收尾
  • 维护者只碰 14–59%——人把时间留给快车道
  • 本质：机器人吸收等待成本，人不陪跑

一句话：这套标签体系不提高「完成率」，它提高的是「维护者时间花在哪」的命中率。7,595 条关闭的 issue 里，被明确标记「能直接修」的那批半天就关、且几乎都是人修的；被标记「卡决策/过期」的那批拖上一个月、但大半是机器人自己关的。人从头到尾只把注意力投在值得修的那一小撮上。

05 · 优先级没在 completed% 上区分，是在「先后」上区分

P0–P3 的 completed 占比确实扁平（54.5%–79.6%），但它们的中位关闭时间排出了一个反直觉但自洽的顺序。

优先级含义completed中位关闭读取
P3低风险清理/文档/打磨54.5%0.2 天「做不做都行」→ 最快拍板，多为 not_planned
P2普通 bug/改进66.6%0.5 天常规活，半天了结
P1紧急回归/现网坏掉79.6%1.0 天completed 最高——真回归必须修，且修得快
P0数据丢失/安全绕过/崩溃循环58.0%8.8 天最慢 紧急但难，要小心修+验证

优先级标签的真实价值：它不预测「修不修」，它给出处理顺序和预期节奏。P1（现网回归）completed 最高、一天就修完——因为这类必须修、路径清晰；P0（数据丢失/安全）反而最慢，因为「紧急」不等于「简单」，恰恰需要小心修、充分验证。这解释了为什么 completed% 在优先级维度拉不开：它的分工就是排序，不是判生死。

06 · 影响维度最扁平，但时间照样分得开

impact 是 completed% 最扁平的一维（23pt），但中位关闭时间从 0.7 天到 10.9 天，仍然拉开 15 倍。impact 标签管的是「坏的是哪块」，间接决定了「谁来修、要多久」。

影响维度的效率：它不回答「修不修」，回答「坏在哪、谁来管、要多久」。data-loss/crash-loop 被标出后走快车道（0.7 天、completed 79%/76%），ux-release-blocker 被标出后知道要跨面协调（10.9 天）。同样的 23pt 扁平 completed% 背后，是 15 倍的时间差——标签在帮维护者按「影响面」预判投入。

07 · 维护者的实际工作路径 一条三层漏斗，人只落三个动作

前面证明的是「效率藏在哪里」；这一节把机制还原成维护者每天真实的处理路径。核心认知：维护者不读 issue 流——机器人把「读」这件事整个扛掉了，人只落在三个必须人做的动作上。来源：README.md（review lane / apply lane / 调度器）、prompts/review-item.md、docs/work-lane.md、src/decision-packets.ts。

01
机器人全自动维护者零参与
issue 一进，调度器按热度排期：最新/活跃的每小时一查（最新边缘 5 分钟一次），30 天内的每天一查，更老的每周一查。Codex（gpt-6.1-sol）只拿 gh api GET 权限做只读审查，产出三样：结构化决策 JSON（复现/优先级/影响/work lane/是否要产品决策）、一条 marker 打标原地编辑的公开评论、一批 advisory 标签。每 15 分钟 apply 一次，只关「未变动、高置信、策略允许」的提案（implemented_on_main、cannot_reproduce、duplicate_or_superseded、stale_insufficient_info 等），每次 checkpoint 最多 40 条，关前重拉现场状态核对。排期、审查、贴标签、写评论、关低价值 issue——全部不占维护者。
02
标签是收件箱过滤器维护者的视图
维护者面对的不是 11,000 条 issue，而是按标签过滤后的几个视图，每条都归好了队：
  • queueable-fix / fix-shape-clear → 修法已写好（workPrompt 连涉及文件、验证命令、什么不能改都给了），等人/让人动手写 PR
  • needs-product-decision → 卡产品方向，要人拍板，同时生成 decision packet（问题+选项+推荐+可能负责人）
  • needs-security-review → 安全敏感，要人判断；needs-maintainer-review → 重要但要人来定优先级/方向
  • good first issue → 已验证的小 bug，社区可接；复现证据 / impact / priority → 给「先修哪个」提供上下文
03
维护者只做机器人做不了的四件事人的决策层
  • 写修复 PR（queueable-fix 车道）：机器人能诊断、能写计划，但不能改代码——人照着 workPrompt 写那个聚焦 PR
  • 拍板 decision packet：产品方向、安全边界、证据够不够、进不进某版本、合并风险——是机器人的建议不是批准，最终要维护者裁
  • 发命令干预：@clawsweeper review / re-review / explain / stop（冻结，贴 clawsweeper:human-review）
  • 兜底保护：维护者自己写的 issue 默认不关（除非证明 main 上已实现）；security / release-blocker / maintainer 硬保护标签绝不自动关

这条路径落到窗口数据上是自洽的：queueable-fix 83% 由维护者关闭（人在写修复）→ needs-product-decision 53% 由 barnacle 关闭（机器人扛掉了「等决策」的收尾）→ stale 75% 由 barnacle 关闭（机器人清场）。维护者不再走「读 issue → 排优先级 → 复现 → 判断 → 关/修」的全流程，而是「标签过滤 → 只碰机器筛出来的三类（写代码、拍板、人工判断）」，剩下九成流水线由 Codex + barnacle 扛掉。

结论 标签体系是「分流机」，不是「完成率优化器」

1 · 量错了指标

completed 占比不区分优先级/影响，是正常的——那两维的职责是排序，不是判生死。效率指标应是「中位关闭时间」和「关闭者身份」。

2 · 时间拉开 60 倍

路由标签把中位关闭时间从 queueable-fix 的 0.5 天拉到 needs-maintainer-review 的 29.4 天——机器人在替你排「先做哪个」。

3 · 人只碰值得修的

快车道 65–84% 由人真修；慢车道 33–75% 由 barnacle 收尾。标签把每个 issue 路由到最便宜的关闭者，人把注意力留给真 bug。
