核心  评级评的是什么

issue-rating: 评的是「报告可验证度」——这条 bug 报告的证据有多硬，而不是问题有多严重。严重度是 P0–P3，产品面是 impact:*，证据强度才是 issue-rating:。三个轴彼此正交：同一个 issue 可以同时是 P1 + impact:auth-provider + issue-rating: 🦞，各说各的，不构成一个总分。

两个易混点，先讲清：① issue 的评级没有字母档位、没有 /6 分数——那套 S/A/B/C/D/F/NA + 分数的尺是 PR 的 rating:；issue 纯粹是 7 个动物标签。② issue 的 issue-rating: 和 PR 的 rating: 借用了同一组动物名但含义与排序都不同：PR 评「可合并准备度」，issue 评「报告可验证度」。引用时不要混用。

01  评分 = 两个字段，一次查表

模型在整个评审里，只对「复现」这件事输出两个结构化字段，其余都是代码在算：

reproductionStatus · 5 值

reproduced / source_reproducible / not_reproduced / unclear / not_applicable —— 回答「这条报告能不能被证实」。

reproductionConfidence · 3 值

high / medium / low —— 模型对自己上面那个判断有多确定。

然后函数 issueRatingLabelForState（clawsweeper-label-selection.ts:149–181）做一次有序匹配，把 15 种组合压缩成 7 个标签。完整矩阵如下（这是代码实际评估的全部组合）：

动物名是查表结果，不是模型自由选择。同一对（复现状态，置信度）永远落同一个标签——所以这套评分可复现、可审计、可写单测。它不像一个「让模型给 1–5 星」的黑盒，而更像一个确定性分类器。

02  端到端流程：从打开到上墙

评级标签不是一次写成的。它经历「预备分流 → 完整评审 → 确定性选标签 → 发布同步 → 路由」五个阶段。

0s
issue 打开。GitHub 表单瞬间打好 bug / enhancement / docs（纯表单选择，无模型参与）。
~分钟
intake 预备分流（小模型 gpt-6-luna）。只读标题与正文（≤ 12 KB 预算、20 秒超时、32 KB 响应上限、无重试），回答三个问题：category（bug / feature / docs / support）、reproduction（缺不缺触发步骤）、environment（缺不缺版本环境）。产出 clawsweeper:intake:* 系列。 这些是预备标签——完整评审发布时第一行就清空，从不直接参与评级。
~分钟
完整评审（Codex，模型上报为 "internal"，只读，返回一个符合 decision schema 的 JSON）。在约 90 个字段里，评级相关的只有两个：reproductionStatus 与 reproductionConfidence。 这就是「评分」的真正发生点——之后全是确定性代码。
发布
确定性选标签 + 发布同步。issueRatingLabelForState 把两个字段映射成唯一一个 issue-rating: 标签；syncIssueAdvisoryLabels（clawsweeper-label-operations.ts:237–315）只增删它拥有的组：clawsweeper:*、issue-rating:*，以及 good first issue / no-stale / stale 联动。 只在 issue 仍 open、评审完整且当前、且非关闭提案时写入；失败 / 过期的报告被跳过，不写评级。
路由
路由与响应。评级本身是信息性的；真正决定去向的是 work-lane 标签（queueable-fix / needs-maintainer-review / needs-product-decision / needs-security-review / linked-pr-open）。同一份评审还会发公开评论，并可能按关闭理由关掉 issue。

一个可验证推论：任何仍带 clawsweeper:intake:* 的 issue，都还没完成一次完整评审。实测 100 个近期开放 issue 中只有 1 个仍带 intake 标签。

03  7 个标签：原话、关闭率、关闭者与已解决关闭占比

每档的英文原话是 ClawSweeper 的 label 描述（GitHub API 逐字）。「关闭率」= 已关闭 / 窗口内总数（快照，任何关闭理由，≠ 已修复）；「关闭中位时间」= 已关闭 issue 从创建到关闭的时长中位；「主要关闭者」= 谁点的关闭按钮（全量）；「已解决关闭占比」= 已关闭中 state_reason=completed 的比例（completed = 已解决 / 有修复落地；对偶 not_planned = 未解决：无法复现 / 不修 / 重复）。窗口 2026-09-13 ~ 11-13，按证据强度从强到弱排列。

关闭中位时间抽样：每档取按创建时间倒序最多 100 条已关闭 issue（🦀 challenger crab 仅 14 条），计算 created→closed 时长中位。存在两个方向性偏差：按「最近创建」排序会低估「活得久」的 issue；窗口右端（临近 11-13）的 issue 可观察的关闭时长更短（右删失）。
主要关闭者 / 已解决关闭占比均为全量（gh api list + Search API，2026-11-15）；「维护者/他人」= 关闭者既非作者也非机器人（无法进一步区分维护者与第三方贡献者）。「已解决」= state_reason=completed，「未解决」= not_planned（无法复现 / 不修 / 重复）。PR 合入的机制事实：openclaw 的 issue 关闭几乎从不带 PR commit——关闭事件上的 commit_id 抽样约 0–3%，说明它不用 PR 的 Fixes #n 自动关闭，而是 bot / 维护者 / 作者把 issue 单独标记成 completed 或 not_planned；timeline 交叉引用抽样显示 completed 多有对应 PR（🦞 100%、🦀 83%、🦐 76%、🦪 52%、🌊 96%），但「交叉引用」偏松（PR 提及即算，含未合并 PR）。表末「PR 合入比例」是精确口径：把每条 issue 的交叉引用 PR 逐个验证 merged 字段（每档抽样 completed 25 条 + not_planned 15 条），再按全量 completed/not_planned 数量加权。结果呈陡降 🦞 88.8% → 🦪 28.4%；注意 🦪 silver shellfish 的 completed 里仅 36% 真有已合并 PR——薄报告常被「已处理」关掉，而非代码修复。

单一关闭率看不清，拆开「谁关 + 怎么关」才有梯度：高置信档（🦞 88.4%、🦀 85.7%）由维护者/他人关闭（🦞 维护者 64% + 作者 24%），且绝大多数是 completed（已解决，有修复落地）。越往下走，两条线同时转：completed 占比跌到 🦐 46.6%、🌊 47.4%，关闭者也从「维护者」换成「作者自关 / barnacle bot」（🌊 作者 45% + barnacle 46%，维护者仅 8%）。也就是说：高评级 = 有人修、修好了才关；低评级 / off-meta = 没人修，作者或机器人按「无法复现 / 不修 / 过期」关掉。一处修正：「修好了」不是 PR 的 Fixes #n 自动关 issue——关闭几乎从不带 PR commit（关闭事件 commit_id 抽样 ≈ 0–3%），而是修复落地后由 bot / 维护者再把 issue 单独标记成 completed。PR 合入比例也同步陡降：🦞 88.8% → 🦪 28.4%——高评级 issue 大多真有代码合入，低评级 / 薄报告即使被标 completed，也常没有对应的已合并 PR。

04  reproductionStatus 的语义：评分的真正依据

评分的根，是模型对「能不能证实这条报告」的判断。五个取值代表五档证据强度，并各自联动一个证据标签：

reproduced
在 current-main 上真实复现了报告的故障。最高证据。（schema 有明确描述）
→ 🦀 · current-main-repro
source_reproducible
源码级可复现：读代码确认 bug 可达，但没实际跑。（schema 有明确描述）
→ 🦞 / 🐚 · source-repro
unclear推断
无法判定：证据不足，说不清能不能复现。
→ 🦐 / 🦪 · needs-info
not_reproduced推断
尝试复现失败，或在 main 上复现不了。
→ 🦪 · not-repro-on-main
not_applicable推断
不适用：不是可验证的 bug（如 feature request）。
→ 🌊 · off-meta tidepool

置信度 confidence 是第二维：同样「源码可复现」，模型很确定就给 🦞 lobster，没那么确定就降 🐚 hermit。所以评分 = 证据类型 + 置信度，两者缺一不可。

诚实标注：schema 只给 reproduced 和 source_reproducible 写了描述（「high-confidence current-main reproduction」「source shows the path without a failing run」）。not_reproduced、unclear、not_applicable 的含义是从标签名、docs/work-lane.md 和映射函数推断出来的，没有逐字的 rubric 原文。

05  评级不做什么

不路由

真正决定 issue 去向的是 5 个 work-lane 标签：queueable-fix（自动修）、linked-pr-open（已有人修）、needs-maintainer-review、needs-product-decision、needs-security-review。评级只回答「真不真」，不回答「谁来修、修不修」。

不预测速度

评级与「关得快」方向相反：🦞 lobster 关闭中位 3.7h，而 🦀 crab 要 32.3h、🦐 shrimp 要 41.4h。它衡量的是证据强度，不是紧急度——关闭快慢更多取决于证据类型是否「好消化」。

结论

01

评级是证据类型分类，不是稀缺度排名。🦞 占 55.6% 因为「源码可复现 + 高置信」是静态分析的常见产物。

02

评分靠确定性查表，不靠模型自由裁量——模型只出两个字段，动物名由代码映射，可复现、可审计、可写单测。

03

评级回答了「真不真」，但「修不修、谁来修」由去向量（work-lane）决定。读 issue 先看五个 work-lane，再看 P 和评级。
