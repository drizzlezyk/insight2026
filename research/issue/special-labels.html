特殊维度：不参与评分的零散标签

前面四个维度都在「打分 / 分类 / 定去向」，这一组标签则各自独立触发、彼此无关：good first issue 招新手、stale/no-stale 管陈腐、bulk-filed 标记批量提报、idea-archive 归档被搁置的想法。它们共同点是都不是评分维度，而是治理与运营的辅助标记。

02 · 触发机制 5 个标签，5 套独立的贴法

与其它维度「一个字段驱动一堆标签」不同，这 5 个标签各有各的触发来源，互不共享一套决策逻辑。

good first issue · 代码硬门槛
由 isGoodFirstIssue() 判定，不是模型直接填的。它要求一条 issue 同时满足 约 14 个条件，是全局最严的标签。
核心条件：type=issue + itemCategory=bug + reproductionStatus=reproduced + reproductionConfidence=high + 三个 requires* 全 false + implementationComplexity=small + autoImplementationCandidate=strict_bug + securityReviewStatus≠needs_attention + workCandidate=queue_fix_pr 且 candidate/high + 有 workPrompt 与 workValidation + 未 opt-out / 未 lock + 非 bulk-filed + 无安全标签 + 无 impact:security + 无保护标签 + 无 open 关联 PR。
stale / no-stale · 陈腐工作流 + 保护
stale 由 GitHub 陈腐工作流在 issue 长期无活动时自动打上；no-stale 是反向保护——当一条 issue 是 queue_fix_pr 候选（issueAdvisoryStateNeedsStaleProtection()），代码主动贴 no-stale 防止它被陈腐流程误关。
clawsweeper:bulk-filed · 批量提报检测
宿主侧检测到同一作者近期高频提 issue（阈值 DEFAULT_BULK_FILER_THRESHOLD=10 条 / WINDOW_DAYS=7 天）时，注入 bulkFiler.detected=true，代码据此贴标签。
clawsweeper:idea-archive · 关闭时归档
在 issue 以 unsponsored_feature_request 关闭时，clawsweeper-apply-close-execution.ts 顺手贴上，把「无赞助的 feature 想法」归档给维护者日后翻看。
feature: ✨ showcase · PR 专用
shouldApplyFeatureShowcaseLabel() 要求 isPullRequest 且 showcase.status=showcase，因此不出现在 issue 上（本次窗口 issue 搜索命中 0，印证了这一点）。

一眼结论：最扎眼的是 stale 与 no-stale 这对镜像——stale 的关闭里有 84.9% 是 not_planned（陈腐 = 被放弃），而 no-stale 的关闭里 98.6% 是 completed（被保护的修复候选最终真被修掉）。两者加起来正好讲清 ClawSweeper 的治理意图：用 no-stale 把「值得修的」从「该陈腐的」里挑出来保护。 good first issue 窗口内只有 2 条，说明 14 条硬门槛把「新手友好」压到了近乎不存在。

结论 特殊标签是「治理辅助」，不是评分

1 · 5 套独立触发

不像其它维度「一个字段驱动」，这 5 个标签各有各的触发源：代码门槛、陈腐工作流、批量检测、关闭归档。

2 · stale / no-stale 是一对镜像

一个标记放弃（85% not_planned），一个保护修复候选（99% completed），合起来是治理的核心逻辑。

3 · good-first-issue 近乎绝迹

14 个同时满足的硬条件，让「新手友好」在窗口内只剩 2 条。
