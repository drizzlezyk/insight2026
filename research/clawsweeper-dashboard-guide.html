OpenClaw · ClawSweeper dashboard field guide · 2026-11-06

Dashboard 有哪些功能？谁在什么场景使用？

基于当前线上页面与仓库文档梳理。核心边界：Dashboard 是只读观察台，不是 GitHub 管理后台。社区维护者通常在仪表盘发现问题，再回到 GitHub Issue/PR 阅读证据、请求复审或作出治理决定。

Dashboard · Observe
看队列、运行健康、覆盖与审查结果

浏览器提供聚合指标和受限的公开引用；不负责执行 GitHub 写操作。

看见 ≠ 操作
GitHub / Operator · Act
评论命令、人工决策、受护栏的 Apply

具体 Issue/PR 的交互发生在 GitHub；部署、凭据和队列运维由授权操作者通过 Actions / CLI / Cloudflare 处理。

01使用角色

社区 / 仓库维护者治理者

看审查与队列是否正常；在 GitHub 查看单条 Issue/PR 的报告、处理待人工决定事项，并按需请求复审。

ClawSweeper 服务操作者运维者

维护 GitHub Actions、Worker、Cloudflare、App 凭据和数据管道；处理部署、积压或基础设施异常。通常是 ClawSweeper 项目的指定维护者。

贡献者 / 公共观察者提交者

通过 GitHub Issue/PR 获得审查反馈、补充复现或环境信息；公共 triage 页面只能查看聚合分类，不提供逐条检索。

02Dashboard 页面地图

Overview · 系统总览

/
维护者 + 运维者

场景 快速判断系统当前是否在工作、是否有明显拥塞或异常。

汇总 Codex 容量、exact review、Apply/close 健康、handoff、活跃 worker、活动管线、fleet coverage 和近期活动，并提供各详情页入口。

适合“先看全局，再决定去哪一页”；不是逐项审批列表。

Agent performance · 执行表现

/agent/
运维者为主

场景 审查变慢、失败增加或同一条目反复被领取时，定位执行层信号。

查看运行时长分位数、按阶段归类的失败尝试、重复 claim 样例及有限的最近历史。

claim 不等于模型执行；重复 claim 本身不能证明浪费算力，也不提供原始日志。

Throughput · 吞吐

/throughput/
维护者 + 运维者

场景 回答“审查量、关闭量和工作流活动近期如何变化”。

展示审查条目数、关闭量、sweep 运行量、创建到最近审查的时间分布，以及 workflow 成功/失败、耗时统计。

这是历史量与趋势；成功运行不代表判断正确，重审会影响最新审查日期统计。

Assessments · 审查评估

/quality/
维护者为主

场景 找出审查记录中曾标记为维护者关注或安全关注的条目。

按记录的评估标记查看关注项和历史记录，可跳转到公开仓库中的对应 GitHub 条目。

反映已保存审查记录，不保证当前仍 open 或仍有效；评估是审查者判断，不是验证过的严重度。

Queue · 队列

/queue/
运维者为主

场景 发现待处理工作积压、退避、搁置、容量压力或发布延迟。

查看 review/publication lane 容量、active/leased/pending/backoff/parked、完成数、失败健康、shed、scheduled feed 与有限 warning evidence。

公开样例有上限且不构成完整清单；页面不提供清队列、重试或改优先级按钮。

Operations · 运行运营

/operations/
运维者为主

场景 判断交接、发布和自动关闭流程是否健康，追踪长时间 handoff。

查看 review flow、handoff incidents、publication backlog/deliveries，以及 close sweep 检查量、关闭量和安全阻断分类。

Apply 汇总有明确范围；它不覆盖所有审查后即时发布操作，也不执行浏览器端写入。

Coverage · 覆盖与新鲜度

/coverage/
维护者 + 运维者

场景 检查参与仓库的观测覆盖和审查证据是否足够新。

呈现公开仓库的计数观察、identity-matched review evidence、集合窗口和覆盖完整性状态。

观测计数与历史报告是不同证据；缺口会显示 Unknown，不会用旧记录伪装成实时覆盖。

Repositories · 仓库视图

/repos/
仓库维护者为主

场景 对比不同仓库的记录量、近期审查、stale open 和关闭情况。

支持筛选仓库并进入单仓概览；仓库卡片可聚合 stale、maintainer、安全关注和近期关闭等记录。

只纳入构建侧确认公开的仓库；基于保存的 corpus，不等于完整实时 GitHub inventory。

Issue triage · Issue 分类概览

/triage
公共观察者

场景 快速了解 ClawSweeper 建议分类的总体分布，如 needs-info、needs-maintainer-review。

展示固定分类视图的聚合计数和数据完整性状态，帮助理解队列构成。

没有逐条 Issue、搜索、标签筛选或详情链接；不能从这个页面分配工作。

PR proof triage · PR 证明分类

/pr-proof-triage
公共观察者

场景 查看 PR proof / 验证类分类的聚合情况。

与 Issue triage 类似，提供隐私受限的类别计数和完整性信息。

不展示 PR 明细、源码诊断或可直接执行的审查动作。

03按角色看：从发现到处理

01 · Observe
Dashboard 发现信号
维护者查看趋势或 Queue；运维者判断积压、失败与 handoff。
02 · Locate
跳回 GitHub 条目
打开公开样例或 Issue/PR，检查审查报告、证据和 advisory labels。
03 · Decide
完成需要人的判断
补信息、验证复现、决定产品行为，或安排安全 / 维护者复核。
04 · Request
按需使用评论命令
@clawsweeper explain、review、re-review 或 stop。
05 · Apply
由授权流程执行
标签同步或满足条件的关闭由独立 Apply 车道完成；不是在 Dashboard 点按钮。

维护者命令的含义：review / re-review 请求只读审查；explain 解释现有结果；stop 阻止后续自动处理并转人工关注。命令会经过仓库权限与当前评论校验，不等于无条件授权任何模型操作。

05读数时要记住的限制

限制实际含义建议解读方式
页面刷新不同步站点构建约每 15 分钟；队列/运行遥测可更频繁；审查总量、评估和关闭汇总约每日两次更新。先看页首的 Snapshot、Reviews、Queue 时间，再判断数据是否足够新。
公开投影有意收窄未认证 observer API 只返回固定聚合字段和 allowlist 范围的公开引用，不返回私有仓库、自由文本、凭据或原始诊断。页面样例是有限观测，不是完整清单；排查具体事件需转 GitHub / 授权运维渠道。
记录 ≠ 实时事实Assessment 和 Repository 页面主要基于已存储报告；历史状态不能证明条目现在仍打开、来源仍匹配或问题已经解决。到 GitHub 核对 live 状态、当前源码与最新报告；“Unknown”不要读成“没有问题”。
官方实例有服务边界官方托管服务针对 OpenClaw / steipete 生态。其它社区接入需自行托管并配置目标仓 dispatcher、App、Worker 与权限。Dashboard 页面可以作为设计参考，不代表第三方仓能直接加入官方实例。

一句话总结：Dashboard 解决“系统现在怎样、哪里值得查”；GitHub 解决“这条 Issue/PR 怎么处理”；受控 Apply 与运维工作流解决“哪些变更可以自动执行”。
