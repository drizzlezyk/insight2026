六条边界

先看限制，再看结论

  • 运行总数是下限。 GitHub Actions API 对单个 workflow 的 total_count 返回上限为 40,000；本报告对达到上限的值标记为 40,000+，累计值因此只能视为下限。
  • 近 30 天数据是样本，不是全量时间序列。 每个 workflow 最多取最近 100 次运行；高频 workflow 的 30 天运行量会被截断，所以“近30天样本”更适合比较失败集中度，而不是精确总量。
  • skipped 不是失败。 该仓库大量使用条件门禁，skipped 是合法的“未命中条件”；成功率统一按 success / (success + failure) 计算，并单独展示 cancelled 与 skipped。
  • 静态安全标记是启发式。 pull_request_target 本身不等于漏洞；本报告进一步检查是否 checkout PR head、是否在 run/script 中直接插值不可信事件字段，再给出结论。
  • 分类是按文件名的人工映射。 129 个文件逐一手工归类，便于叙事；跨类别复用（例如发布流程里的 CI 检查）不会被重复计数。
  • 关于 122 与 129。 提问中提到的 122 与当前 main 分支的 129 有 7 个差异；Contents API 在本次快照返回 129 个全部 active 的 YAML。报告按 129 个全量分析，若需对齐某一历史时点，可按附录中的文件清单核对。

发现与建议：从“能跑”到“可治理”

08 / FINDINGS

把上面的数字收束成一句话：这是一个安全卫生很好、平台化程度很高、但运营复杂度已经接近临界点的 CI/CD 系统。 最该做的不是“再加一个 workflow”，而是给现有 129 个 workflow 建立分类、生命周期和可靠性语义。

01

P1手动优先的控制面，是优势也是单点

108 个 workflow 支持手动触发，45 个仅手动，475 个输入项分布在 78 个文件。发布、证明、跨端验证都靠人拉闸。

优势是可控、可审计、能在故障时人工介入；风险是发布知识集中在少数人、输入面过大、重复操作多。建议把高频手动流程逐步产品化：固定默认值、减少输入、增加预检，把“人拉闸”变成“人确认”。
02

—供应链卫生接近满分，是真正的强项

1,262/1,262 action 引用 SHA 固定；0 write-all、0 secrets:inherit、0 不可信事件插值进 shell/script；5 个 PR target 均不 checkout PR 代码。

这不是“看起来安全”，而是结构性安全：攻击面小、权限低、外部代码不执行。建议保持，并把 zizmor/actionlint 做成强制门禁；对 21 处显式豁免做季度复核。
03

P1workflow sprawl 与巨型文件并存

Actions 注册表 348 条记录，当前 129 个文件之外还有 219 条历史记录；ci.yml 7,475 行、43 个 job，占全部 YAML 的 10.7%；前 5 个文件占 32%。

巨型文件让 review、复用和故障定位都变贵；历史记录让“到底有多少条流水线”变得不可读。建议把 ci.yml 拆成 reusable workflow + 小型入口，建立 workflow owner 清单，并清理长期 disabled/无运行的注册记录。
04

P0失败高度集中在发布与证明链路

近 30 天样本 1,016 次失败，Top 10 占 56%；OpenClaw Performance（93 失败/5 成功）、Full Release Validation（89/4）、Release Publish（61/29）、Plugin Prerelease（60/37）最突出。

这可能是 fail-closed 门禁的预期行为，也可能是 flaky / 配置漂移。建议先做失败分类：基础设施、真实回归、预期拒绝、配置错误；对前两类分别处理，对预期拒绝显式标记，不要用“失败”承载所有语义。
05

P0timeout 与 concurrency 是最大的运营缺口

161 / 471 个 job 没有 timeout；28 个文件完全没有 concurrency；docker-image-refresh 的 p95 达到 30 天。

没有 timeout 的长任务会占用 runner、拖长反馈、放大取消/重试成本；没有 concurrency 的 bot/校验工作流会在事件风暴下重复执行。建议把 timeout-minutes 和 concurrency 纳入 workflow-sanity 的强制检查，并为长任务设置显式上限。
06

P2长尾里有休眠与“只复用”工作流

10 个零运行（8 个仅复用 + 2 个手动）；44 个运行不足 100 次；45 个仅手动。22 个 workflow 最近一次运行以失败结束。

零运行不一定等于死代码：仅复用 workflow 可能被外部仓库调用。建议在文件头或元数据中标注“reusable / manual / scheduled”，并增加 90 天无运行 review，把“有意保留”和“忘记删除”分开。
07

P2调度碰撞与分钟级惊群

5 个 workflow 使用相同的 23 * * * *；Security Review 每 10 分钟一次（144 次/天）；07:00 UTC 一周累计 148 次触发。

同一分钟启动会放大 runner 争抢和 API 限流。建议给 cron 加抖动/错峰，合并同频校验，评估把每小时任务改成事件驱动或批量检查。
08

P2secret 面宽，AI provider key 尤其多

61 个文件引用 secrets，共 117 个唯一名称；OPENAI_API_KEY 出现在 23 个文件，ANTHROPIC_API_KEY / MINIMAX_API_KEY 各 12 个；42 个 workflow 提及 AI/LLM。

AI e2e 需要真实 key，但宽注入会放大泄露与轮换成本。建议使用受保护 environment、按 job 注入、优先 OIDC 短期凭证，给 provider key 建立轮换与最小权限策略。

指标定义
SHA 固定action 的 uses ref 为 40 位十六进制 commit SHA；tag / branch 视为未固定。
执行conclusion 不为 skipped 且不为 null 的运行。
完成成功率success / (success + failure)；cancelled 与 skipped 不计入分母。
并发覆盖文件级 concurrency 或任一 job 级 concurrency；job 级覆盖单独计数。
timeout 覆盖job 显式声明 timeout-minutes；文件级“全覆盖”指所有 job 都有。
计划次/天对 cron 的 minute/hour 做展开并乘以 dom/dow 比例；周/月级 cron 为近似值。
失败热点近 30 天样本中 conclusion=failure 的运行数；不是全量 30 天总数。
运行量分层使用 Actions API 的 total_count；达到 40,000 视为封顶。
已注册历史Actions 保留已删除 workflow 的注册记录；当前文件之外的部分按历史记录计。
分类按文件名逐一手工映射到 14 个类别；跨类别复用不重复计数。
