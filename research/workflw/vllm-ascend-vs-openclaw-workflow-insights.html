基线与规模：不是谁更大，而是谁更重

01 / BASELINE

先把“可比性”说清楚：OpenClaw 是一个 129 个 workflow、69,776 行、3,168 个 step 的发布/证明平台；vLLM-Ascend 是一个 57 个 workflow、18,394 行、722 个 step 的硬件社区 CI。OpenClaw 在绝对规模上大约是 vLLM 的 2–4 倍，但两者的中位 workflow 都只有 2 个 job，真正的差异在“长尾怎么长”。

OpenClaw 的形状

少数巨兽 + 长尾

头部ci.yml 一个文件 7,475 行、43 个 job，占全部 YAML 的 10.7%；前 5 个文件占 32%。

vLLM-Ascend 的形状

设备变体 + PR 门禁

头部pr_nightly_command.yml 1,090 行、12 个 job；pr_test.yaml 1,061 行、10 个 job。最大文件只有 OpenClaw 的 1/7。

运行3 个 workflow 达到 40,000 上限（E2E、PR Create、Merge Conflict Labeler），PR 反应式自动化占运行量的大头。

组合结构：发布重型 vs 测试重型

02 / PORTFOLIO

两套 workflow 的“职能组合”几乎相反。OpenClaw 最大的一块是发布/分发（33 个，25.6%），随后才是 CI 与社区机器人；vLLM-Ascend 最大的一块是 Nightly/Weekly 测试（20 个，35.1%）和 PR 门禁/机器人（17 个，29.8%），两者合计 64.9%。这不是谁更先进，而是社区所处的阶段不同：一个在把发布与证明产品化，一个在把 PR 反馈与设备覆盖做厚。

一句话对比

组合决定治理重点

OpenClaw 的重点是“发布链路 + 安全供应链”。 33 个发布/分发 workflow、10 个安全/供应链 workflow，失败热点也集中在 release/proof。
vLLM-Ascend 的重点是“PR 反馈 + 设备矩阵”。 20 个 nightly/weekly、17 个 PR 门禁/机器人；运行量最大的是 PR 反应，失败最多的是硬件 nightly。

因此，vLLM 不应该照搬 OpenClaw 的 33 个发布 workflow；它更该借鉴的是 OpenClaw 的安全卫生、超时/并发治理和复用分层。

触发与控制面：UI 表单 vs 评论命令

03 / CONTROL

两边的“手动控制面”不是同一种东西。OpenClaw 用手动表单：108 个 workflow 支持 workflow_dispatch，475 个输入项，45 个只能手动触发；它适合发布经理在 UI 上选择 target、runner、release scope。vLLM-Ascend 用 PR 评论命令：23 个 workflow_dispatch + 9 个 repository_dispatch，其中 8 个是 /run、/e2e、/nightly 等命令处理器，更适合贡献者在 PR 里直接触发。

调度：原生 cron vs 中央 orchestrator

谁在真正决定什么时候跑

OpenClaw33 个原生 schedule，估计 411 次/天；5 个 workflow 共用 23 * * * *，07:00 UTC 是峰值（148 次/周）。调度可见，但容易碰撞。
vLLM-Ascend只有 6 个原生 schedule（28.5 次/天），但 20 个 Nightly/Weekly 类别 workflow 中，13 个是调度入口（多数 dispatch-only），7 个是 _ reusable helper；schedule_daily_test 和 pr_nightly_command 里有 14 处 gh workflow run，真实周期负载远高于 28.5/天。
启示中央 orchestrator 更适合稀缺 NPU 容量，但必须补运行账本、幂等键和重复 dispatch 检测；否则“谁在什么时候触发了什么”会比原生 cron 更难追踪。

Runner 与容量：云托管 vs 昇腾舰队

05 / RUNNER

OpenClaw 的 runner 抽象

值得借鉴，但不要照抄复杂度

机制用 vars.OPENCLAW_CI_RUNNER_BACKEND、inputs.runner_group 和 preflight outputs 在 GitHub-hosted / Blacksmith / Boat / Runson 之间切换；73 个 job 使用多后端动态表达式。
优点同一套 workflow 可以在不同容量池上运行；故障时可以切回 GitHub-hosted；release 与 CI 共用同一套 runner 选择逻辑。
代价可读性差、调试难、表达式本身就是风险面。vLLM 不需要 73 个多后端表达式。

vLLM 的容量启示

静态标签 + 稀缺设备

优势静态标签（a2b3-0、a3-800t-0、a5-0、310p）比动态表达式更透明，便于容量规划和排障。
缺口13 个动态标签仍然存在；NPU job 的 timeout 覆盖率只有 8.0%，一旦挂起就会占用稀缺设备。
建议保留静态设备标签；加一层很小的映射/校验（SoC → label → timeout），不要引入 OpenClaw 式的多后端抽象。先补 concurrency、timeout 和队列时长观测。

可靠性：整体接近，失败集中度不同

启示清单：该抄什么，不该抄什么

08 / LESSONS

把对比收束成一句话：vLLM-Ascend 不该复制 OpenClaw 的规模与发布复杂度，但应该复制它的安全卫生、超时/并发治理和“入口薄、helper 厚”的复用思路。 vLLM 真正需要的，是在保留评论命令与设备矩阵的前提下，把可靠性、供应链和容量治理补起来。

01

P0先补安全卫生，不要先补发布流程

vLLM 最紧的差距不是“发布自动化不够”，而是 269 / 284 个 action 引用未固定 SHA、19 个文件没有 permissions、172 / 187 个 job 没有 timeout。把 top 6 action 固定、给 19 个文件补 permissions、给 172 个 job 补 timeout，是 30 天内最确定的收益。

数据：SHA 固定率 5.3% vs OpenClaw 100%；timeout 8.0% vs 65.8%；top 6 action 覆盖 80.6% 的引用。
02

P0保留评论命令，但把它变成可审计的控制面

vLLM 的 8 个 /命令处理器（9 个 repository_dispatch 中 8 个是命令、1 个是分发器）比 OpenClaw 的 475 个 UI 输入项更适合社区。但 slash_command_dispatch（28.5k 运行）、bot_merge_conflict（40k）、bot_pr_create（40k）、pr_nightly_command（4.3k）都没有 concurrency；命令链路是 issue_comment → repository_dispatch → handler → 再触发 workflow，必须补授权、幂等键、冷却时间和运行账本。

数据：26 个文件无 concurrency；pr_nightly_command 与 schedule_daily_test 都通过 gh workflow run 调起同一批 nightly。
03

P0可靠性要“修点”，不要“全面重试”

vLLM 的 Top 10 失败 workflow 占近 30 天失败的 79%，远高于 OpenClaw 的 56%。Nightly-A5 的失败率 86.1%，A3-560T 66.7%，Schedule Daily 75.7%，/e2e 63.6%，E2E-upstream 93.1%，Test Coverage 在样本中 0 成功。先做失败分类和 quarantine，再决定哪些重试。

数据：近 30 天 605 次失败，Top 10 = 477 次；Nightly-A5 68 失败 / 11 成功。
04

P1把 9 个设备变体收进一个 reusable workflow

5 个 nightly + 4 个 weekly 设备 workflow 合计 3,936 行、74 个 job、94 个输入项、34,617 次运行，占全部 dispatch 输入的 81.7%。它们覆盖 A2/A3/A3-560T/A5/310P，很多逻辑重复。用一个参数化 reusable workflow + device matrix，保留 SoC 差异步骤，可以显著降低维护面。

数据：设备变体占 YAML 行 21.4%、job 39.6%、dispatch 输入 81.7%。
05

P1中央调度适合稀缺 NPU，但必须可观测

vLLM 只有 6 个原生 schedule，但 20 个 nightly/weekly 中 13 个是调度入口（多数 dispatch-only）、7 个是 _ helper，由 14 处 gh workflow run 调起；这比 OpenClaw 的 411 次/天、5 个 23 * * * * 碰撞更适合稀缺设备。代价是“谁在什么时候触发了什么”更难追踪。建议统一 orchestrator、加运行账本和重复 dispatch 检测。

数据：Nightly/Weekly 类别 35,473 次历史运行；OpenClaw 33 个原生 schedule、411 次/天。
06

P1保留静态设备标签，不要过度抽象 runner

vLLM 80.8% 的 runner 是自建 CPU/NPU，静态标签（a2b3-0、a3-800t-0、a5-0、310p）比 OpenClaw 的 73 个多后端动态表达式更透明。需要补的是 timeout、concurrency、队列时长和 SoC → label 的轻量映射，而不是一整套多后端抽象。

数据：vLLM 97 / 120 自建；13 个动态标签；OpenClaw 73 个多后端动态表达式。
07

P2不要为了“像 OpenClaw”而增加发布 ceremony

vLLM 只有 1 个 release workflow、7 个 image workflow；OpenClaw 有 33 个 release/分发 workflow。vLLM 的发布面并不缺“数量”，缺的是镜像/轮子发布的可重复性和测试可靠性。把 release 自动化控制在必要范围，把精力放在 nightly 与 PR 反馈上。

数据：vLLM release 1 / 57（1.8%）；OpenClaw release 33 / 129（25.6%）。
08

P2把 _ 约定升级为生命周期制度

vLLM 的 13 个 _ workflow 全部 reusable-only，11 个零运行是合理设计；但 Actions 注册表已有 145 条记录，是当前文件的 2.5 倍。建议给每个 workflow 加 owner/用途/生命周期元数据，标记 reusable-only，定期归档无运行记录。

数据：vLLM 145 记录 / 57 当前；OpenClaw 348 / 129（2.7×）。

口径与限制

先看边界，再看结论

  • 运行总量是下限。 Actions API 对单个 workflow 的 total_count 上限为 40,000；OpenClaw 有 23 个封顶，vLLM 有 3 个。
  • 近 30 天是样本。 每个 workflow 最多取最近 100 次；高频 workflow 的 30 天量会被截断，适合比较失败集中度，不适合精确总量。
  • skipped / cancelled 不是失败。 成功率统一按 success / (success + failure)，cancelled 与 skipped 另列。
  • 分类是人工映射。 OpenClaw 14 类、vLLM 7 类；跨类别复用不重复计数。
  • vLLM 的 _nightly_image_build 时长异常。 部分运行记录从 2025-12 创建、2026-11 才更新，约 340 天，已从慢任务表排除。
  • OpenClaw 的 122 vs 129。 本报告使用其 129 个当前文件的全量分析；提问中的 122 与当前 main 快照相差 7 个。
